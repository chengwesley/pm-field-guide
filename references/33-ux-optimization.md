# 33 用戶體驗優化

> 一句話：找出已上線流程中真正讓用戶卡住或放棄的那幾個點，修掉它，並用數據確認真的變好，而不是只是變不一樣。

## 何時用

- 某個流程的完成率、留存或客訴長期不理想，但說不出問題在哪。
- 客服反映同一類問題反覆出現（「找不到」「不知道下一步」「以為已經送出」）。
- 新功能上線後採用率低，懷疑是體驗問題而不是需求問題。
- 何時不需要：問題根源是需求本身不成立（用戶根本不需要這功能），那該回到需求分析；或流程使用量太小，優化的收益不值得投入。

## 動手前先問

1. **要優化的是哪一段流程，終點是什麼？** 例如「從選定房型到成功完成訂房」。若沒答：先假設是該產品最核心的一條任務流程。
2. **現在的基準數字是多少？** 完成率、平均耗時、該流程的客訴量。若沒答：先假設沒有基準，第一步就是建立基準，不要直接改。
3. **有哪些現成的線索？** 埋點、客服紀錄、App 評論、過去的易用性測試。若沒答：假設只有客服紀錄與漏斗數據，用這兩者先開始。
4. **有沒有不能動的限制？** 法規要求的步驟（例如線上刷卡的身分驗證）、品牌規範、技術限制。若沒答：假設法規步驟不能刪，只能改呈現方式。

## 做法

1. **先建基準，再找問題。** 確認要看的 1 個主要指標（例如完成率）與 1–2 個護欄指標（例如錯誤率、客訴量）。判斷標準：拿到過去 4 週（假設值）的穩定數字才開始改，否則改完無從比較。
2. **用三種來源交叉定位摩擦點。**
   - 量化：漏斗每一步的流失、停留時間異常長的頁面、重複點擊或返回。
   - 質化：客服紀錄按問題分類計數、App 評論關鍵字、5 位用戶的任務觀察。
   - 專家：用下方啟發式評估自己走一遍。
   判斷標準：至少兩種來源指向同一個點，才列為「確認的摩擦點」；只有一種來源支持的，列為「待驗證」。
3. **做啟發式評估。** 以 Nielsen 的十項可用性啟發式為底，PM 實務上最常抓到問題的是這五項：

| 檢查點 | 問自己 |
|---|---|
| 系統狀態可見 | 用戶按下去之後，知道有沒有成功嗎？ |
| 符合用戶的語言 | 按鈕寫的是用戶的話，還是工程的話？ |
| 錯誤預防 | 能不能在用戶犯錯前就攔下來？ |
| 辨識而非回想 | 用戶需要記住上一頁的資訊嗎？ |
| 錯誤訊息可行動 | 錯誤訊息有說「接下來怎麼辦」嗎？ |

4. **排優化順序。** 每個摩擦點估三件事：影響人數（經過這步的用戶數 × 流失率）、嚴重度（擋住任務／拖慢／只是不舒服）、修改成本（人天）。判斷規則：先做「影響人數高 × 擋住任務 × 成本低」；成本高的要另外寫提案，不要塞進優化迭代。
5. **一次只改一個變因，或用 A/B 測試。** 同時改文案、版面、步驟，變好了也不知道是哪個有效，變差了也無法回退單一項。流量夠就做 A/B；流量不夠就改前後比較，並記錄同期的外部事件。
6. **事前寫定「怎樣算變好」。** 例如「完成率從 ____% 提升到 ____%，且錯誤率不上升」，觀察期 ____ 天。判斷標準：觀察期結束時，答案只有達標、未達標、無法判斷三種。
7. **回頭檢查摩擦有沒有被移到別處。** 例如減少註冊步驟後，註冊完成率上升，但首次使用時要補填資料，整體啟用率沒變。看下一段流程的指標，確認不是把問題往後推。

### 個資提醒

用戶錄影、Session Replay、熱點圖、訪談錄音都屬於個資蒐集。實務上：事先告知並取得同意、錄影工具遮蔽輸入欄位與敏感內容、只保留分析需要的期間、分享給團隊時去識別化。訂房、電商等處理付款資料的產品，絕不可錄下卡號與證件資料。符合台灣個資法、GDPR、CCPA 的告知同意與最小蒐集原則。

## 產出模板

- **報告格式：** 完整報告（外框見 `modes/report.md`）
- **標題：** 體驗優化計畫：____（流程）
- **結論先講：** 本輪只改 ____；成功門檻是 ____ 從 ____ 到 ____。

## 品質檢查

- [ ] 改之前有基準數字，而且基準期間沒有異常事件。
- [ ] 每個摩擦點都寫出證據來源，至少兩種來源的才列為確認。
- [ ] 本輪優化只改一個變因，或有 A/B 對照。
- [ ] 成功門檻與觀察期在上線前寫定。
- [ ] 有看下游流程的指標，確認問題沒有被往後推。
- [ ] 用戶錄影、訪談資料有告知同意與保存期限。

## 常見錯誤

- **憑感覺改版** → 團隊覺得「這頁很醜」就重做，上線後數字沒變 → 先找證據，醜但沒人卡住的頁面不是優先。
- **同時改五個地方** → 完成率上升 3%，沒人知道是哪個改動有效，下次無法複製 → 拆成多輪，或用 A/B 分組測。
- **把客訴最大聲的當最嚴重** → 少數重度用戶反覆抱怨，資源被拉走，大多數人卡住的地方沒人管 → 用影響人數 × 嚴重度排序，大聲的客訴只當線索。
- **觀察期太短就下結論** → 上線兩天數字上升，其實是新奇效應或週間波動 → 觀察期至少涵蓋一個完整週期，並對照去年或上月同期。
- **只看被優化的那一步** → 那一步轉換上升，整體完成率沒動 → 主要指標永遠用流程終點，不是單一步驟。

## 情境範例

訂房網站結帳流程，客服反映用戶常以為已訂好房，其實停在付款前那一步。

- 基準：選定房型到完成付款的完成率 ____%（假設值 58%），過去 4 週穩定。
- 量化證據：漏斗顯示「填寫付款資訊」頁流失最大；質化證據：客服紀錄中「以為訂好了」類問題每月 ____ 件（需查證）。
- 啟發式：違反「系統狀態可見」，頁面沒有顯示「尚未完成訂房，還差一步」。
- 本輪只改一處：在該頁頂部加入進度條與「還差 1 步」提示。
- 成功門檻：完成率從 58% 到 63%（假設值），付款失敗率不上升，觀察 14 天。
- 下游檢查：確認訂房後的取消率沒有上升。
- Session Replay 遮蔽卡號與證件欄位，符合個資法規。
