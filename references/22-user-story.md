# 22 User Story

> 一句話：把需求切成「一個角色能完整得到一個價值」的小塊，讓團隊每個 sprint 都交付能用的東西，而不是一堆做一半的元件。

## 何時用

- PRD 已定案，要拆成 backlog 項目讓 RD 估時、排 sprint。
- 一個需求大到一個 sprint 做不完，需要切片又不想切成「前端一張、後端一張」。
- 需求方和 RD 對「做完」的定義不同，需要用故事加驗收條件對齊。
- 何時不需要：純技術工作（升級套件、重構、建 CI）不必硬套「身為使用者」，寫成 technical task 並註明它支撐哪個故事即可；bug 也直接寫重現步驟。

## 動手前先問

1. **這個故事的角色是誰？** 不是「使用者」，是有具體權限與情境的角色（企業管理員、外部協作者、免費版用戶）。
   若沒答：從 PRD 的使用者情境表挑最主要的角色，其餘角色另開故事。
2. **他要達成的結果是什麼，為什麼重要？**
   若沒答：用 PRD 目標反推價值，標「待需求方確認」。
3. **最小能交付價值的版本是什麼？**
   若沒答：先切出「只走主流程、只支援一種輸入」的版本當第一片，其他當後續故事。
4. **團隊的故事大小上限？**（例如一個故事不超過 ____ 點或 ____ 天）
   若沒答：假設一個故事要能在半個 sprint 內完成。

## 做法

1. **寫故事句型。** 「身為〈角色〉，我想要〈能力〉，以便〈價值〉。」判斷標準：「以便」後面如果只是重複前面（「我想要匯出，以便匯出檔案」），代表還沒想清楚價值，回頭問。
2. **用 INVEST 逐條檢查：**
   | 字母 | 檢查問題 | 不通過時怎麼辦 |
   |---|---|---|
   | Independent | 能不能不等別的故事就開始做、單獨上線？ | 合併有強依賴的，或調整切法 |
   | Negotiable | 寫的是要達成什麼，還是把 UI 寫死了？ | 刪掉實作細節，移到設計稿 |
   | Valuable | 單獨上線後，角色真的得到了什麼嗎？ | 若只是「API 完成」，改用垂直切片 |
   | Estimable | RD 能估嗎？不能的話缺什麼資訊？ | 開 spike（限時調查）先釐清 |
   | Small | 能在團隊上限內完成？ | 用下方切片法拆 |
   | Testable | 有驗收條件嗎？ | 補 Given/When/Then（見 23） |
3. **垂直切片，不要水平切。** 每片都穿過 UI、邏輯、資料三層，只是範圍變窄。常用切法：
   - 依流程步驟：先做「建立」，再做「編輯」、「刪除」。
   - 依規則變化：先支援一種規則，再加例外。
   - 依資料種類：先支援 CSV，再支援 Excel。
   - 依角色：先管理員，再一般成員。
   - 依品質：先手動可用，再自動化、再優化效能。
   - 依主流程／異常：先 happy path，再補錯誤處理（但錯誤處理不可拖到上線後）。
4. **拆 Epic。** Epic = 一個 PRD 目標，底下 3–10 個故事。拆法：先列出 Epic 的完整使用旅程，在每個步驟問「最少要什麼才能走過去」，那些是第一批故事；其餘排後面。判斷標準：第一批故事全部完成時，角色能端到端走完一次主流程。
5. **補驗收條件與 DoD。** 故事卡上掛 3–7 條驗收條件；DoD（完成定義）是團隊共通的，不用每張重寫。
6. **跟 RD 一起 refinement。** 故事寫完不是丟過去，而是在 refinement 會議中被挑戰。RD 問倒你的地方，就是故事要補的地方。

## 產出模板

- **報告格式：** 完整報告（外框見 `modes/report.md`）
- **標題：** User Story：____（Epic）
- **結論先講：** 這個 Epic 拆成 ____ 則故事；第一批 ____ 則做完後，使用者能 ____。

下面是本文的模板。

```markdown
### Epic：____（對應 PRD 目標 G__）
- 目標使用者：____
- 端到端旅程：____ → ____ → ____ → ____
- 第一批故事完成時，使用者能：____

### Story ____-01：____（短標題，動詞開頭）
**故事**
身為 ____（具體角色），
我想要 ____（能力），
以便 ____（價值／結果）。

**背景**：____（為什麼現在做、相關 PRD 連結 ____）

**驗收條件**
- AC1：Given ____ When ____ Then ____
- AC2：Given ____ When ____ Then ____
- AC3（異常）：Given ____ When ____ Then ____

**不在此故事範圍**：____（放到 Story ____-0_）

**依賴**：____（無 / 故事 ____ / 外部 ____）
**設計稿**：____
**估點**：____　**優先級**：Must・Should・Could
**INVEST 自檢**：I ☐ N ☐ V ☐ E ☐ S ☐ T ☐
```

## 品質檢查

- [ ] 角色是具體角色，不是「使用者」或「系統」。
- [ ] 「以便」後面寫的是對角色的結果，不是功能本身的重述。
- [ ] 這個故事單獨上線，角色就能感受到差異（不是「後端 API 完成」）。
- [ ] 沒有把按鈕位置、顏色、元件名稱寫進故事句，那些留給設計稿。
- [ ] 每個故事至少一條異常路徑的驗收條件。
- [ ] Epic 的第一批故事能串成一次端到端可走完的主流程。
- [ ] 每個故事都有「不在此故事範圍」，避免 RD 自行擴大或縮小。

## 常見錯誤

- **水平切片（前端一張、後端一張、DB 一張）** → 習慣照分工切 → 單張做完沒有價值，到最後一張才能驗收，風險全堆在尾端。改：每張都穿三層，範圍變窄而不是層次變少。
- **以「身為系統」開頭** → 想把技術工作塞進故事格式 → 價值欄寫不出來，排序時永遠被擠掉。改：寫成 technical task，標明它解鎖哪個故事。
- **故事寫成規格書** → 怕 RD 做錯，把所有細節塞進去 → 失去討論空間，RD 照字面做出不合理的東西。改：故事寫意圖，細節放驗收條件與設計稿。
- **異常處理延後成獨立故事，然後被砍** → 為了趕上線先做 happy path → 上線後客服接到大量「卡住了」。改：關鍵異常（失敗、無權限、重複提交）的驗收條件必須跟主故事同時完成。
- **Epic 拆完沒有 MVP 線** → 按功能清單平鋪 → 做了一半的每個功能，沒有一條路能走完。改：用故事地圖畫一條橫線，線上的全部做完才算第一次可交付。

## 情境範例

電商「以圖搜尋商品」Epic 拆分：

- 旅程：拍照或選圖 → 框選商品 → 執行搜尋 → 瀏覽結果 → 進入商品頁。
- Story IMG-01：身為電商 App 會員，我想要上傳一張商品照片找到相似商品，以便不必猜關鍵字。
  - AC1：Given 已選擇一張 ____ MB 內（假設值）的商品照片，When 點「以圖搜尋」，Then 顯示相似商品列表，點任一商品可進入該商品頁。
  - AC2（異常）：Given 搜尋中斷網或關閉 App，When 重新開啟，Then 原本的瀏覽頁面與購物車未受影響，並提示可重新搜尋。
  - 不在此故事範圍：一張照片多件商品分別搜尋（IMG-03）、以圖搜尋歷史紀錄（IMG-04）。
- Story IMG-02：身為會員，我想要在搜尋前框選照片中的商品範圍，以便背景雜物不干擾結果。
- 第一批 = IMG-01 + IMG-02，完成後能端到端走完一次。
- 個資提醒：上傳的照片可能拍到人臉或住家環境，需告知用戶照片會上傳、處理後保存多久、是否用於模型訓練等其他用途。
