# 42 RD 溝通

> 一句話：讓 RD 拿到一份不用猜的需求，估時用談的不用壓的，技術取捨交給該決定的人。

## 何時用

- 需求要交給 RD 開工前的 kickoff 或 refinement。
- RD 估出來的時間比你預期長很多，你想談。
- 開發中途需求要改（業務追加、設計調整、法規變動）。
- RD 提出「這樣做比較好」的技術方案，跟你原本想的不同。

何時不需要：純技術重構、RD 自主的工程改善（PM 只需知道影響範圍與時程）。

## 動手前先問

1. **這個需求要解決什麼問題、成功長什麼樣？** 若沒答：先回頭補 PRD 的問題與成功指標，不要直接拿解法去開會。
2. **有沒有硬期限？硬在哪？** 若沒答：假設沒有外部硬期限，時程以 RD 估時為準，再跟需求方確認。
3. **哪些是不能讓步的，哪些可以談？** 若沒答：先列出你認為的 must-have，在會議上請 RD 挑戰。
4. **誰是這個功能的技術負責人？** 若沒答：請 RD 主管指派，不要預設是最資深的那位。

## 做法

1. **檢查需求是否講清楚。** 交出去前自己對照下表，任一項答不出來就還沒準備好：

   | 項目 | 判斷標準 |
   |---|---|
   | 為什麼做 | 一句話講得出問題與受影響的使用者 |
   | 範圍 | 有寫「不做什麼」 |
   | 流程 | 正常路徑＋至少 3 個異常情境（空值、權限不足、網路中斷等） |
   | 驗收條件 | 可以被測試，不含「順暢」「友善」這種詞 |
   | 依賴 | 設計稿、API、法務、第三方是否到位 |

2. **開 refinement，讓 RD 先問。** 先講問題與成功標準 5 分鐘，剩下時間讓 RD 提問。判斷標準：RD 問的問題你答不出來的，記成待辦並承諾回覆日期，不要當場拍腦袋。
3. **估時用拆的，不用壓的。** RD 估得比你想的長，問「哪一塊最花時間？為什麼？」，而不是「能不能快一點」。找到大頭後，討論能不能縮範圍、分階段、或換做法。判斷標準：時間縮短必須對應到某個範圍或品質的取捨，寫得出來才算數。
4. **分清楚決策權。**

   | 決策 | 誰決定 | PM 的角色 |
   |---|---|---|
   | 做什麼、為誰做、先後順序 | PM | 決定並說明理由 |
   | 怎麼做（架構、技術選型、實作方式） | RD | 提供限制條件，不指定做法 |
   | 時間 vs 範圍 vs 品質的取捨 | PM 與 RD 共同 | PM 提供商業代價，RD 提供技術代價 |

5. **處理需求變更。** 任何變更先評估三件事：影響哪些已完成的工作、要多花多久、要拿掉什麼來換。判斷標準：沒有「拿掉什麼」的變更，等於默默把時程加長。變更寫進文件並標註版本與日期。
6. **開發中保持可被找到。** RD 卡住時回覆要快。約定一個管道（例如專案頻道）並承諾工作時間內 ____ 小時內回覆。

### PM 不該做的事

- 指定 RD 用哪個框架、怎麼切資料表（除非是業務規則）。
- 繞過 RD 主管直接找工程師插單。
- 在 RD 面前承諾業務一個沒估過的日期。
- 開發中途口頭改需求、不更新文件。
- 把 RD 的估時直接打折後對外報。

## 產出模板

```markdown
### 需求交付卡
- 需求名稱：____　PRD 連結：____
- 要解決的問題：____
- 成功標準：____（指標＋門檻）
- 範圍內：____
- 範圍外（這次不做）：____
- 異常情境：1. ____ 2. ____ 3. ____
- 依賴與狀態：設計 ____／API ____／法務 ____
- 硬期限與原因：____
- 待回覆問題：____（負責人 ____，回覆日 ____）

### 需求變更紀錄
| 日期 | 變更內容 | 提出人 | 影響工作 | 時程影響 | 拿掉／延後的項目 | RD 確認人 |
|---|---|---|---|---|---|---|
| ____ | ____ | ____ | ____ | ____ | ____ | ____ |
```

### 話術

- 估時太長時：「這個估時我想理解得更細。哪一段最花時間？如果那段我們先不做，剩下大概多久？」——把談判變成拆解，RD 不會覺得被質疑專業。
- RD 提出不同方案時：「你這個做法對使用者會有什麼不同？如果使用者感受一樣，就照你的方式做。」——守住 PM 該守的（使用者結果），放掉該放的（實作）。
- 需求變更時：「這個改動我評估要多 ____ 天。我建議把 ____ 移到下一版來換，你看技術上可行嗎？」——變更一定帶著交換條件出現。

## 品質檢查

- [ ] 需求交付卡的「範圍外」不是空的
- [ ] 異常情境至少 3 個，且是這個功能特有的
- [ ] 驗收條件裡沒有無法測量的形容詞
- [ ] 估時調整都對應到一個寫得出來的範圍或品質取捨
- [ ] 需求變更都有紀錄，且每筆都寫了拿掉什麼
- [ ] 對外報的日期是 RD 確認過的，不是 PM 自己打折的
- [ ] 待回覆問題都有負責人與日期

## 常見錯誤

- **「這個應該很簡單吧」** → 從使用者介面看簡單，不代表後端簡單，這句話會讓 RD 覺得估時不被信任 → 改問「哪裡比看起來複雜？」
- **一次丟完整份 PRD 就期待開工** → RD 讀文件的理解跟你腦中的畫面不同 → 一定要開 refinement，讓 RD 用自己的話講一遍需求。
- **用 deadline 壓估時** → RD 會給一個你想聽的數字，然後加班或偷工 → 先拿到誠實的估時，再談範圍取捨。
- **技術方案也要拍板** → PM 指定實作方式，出問題時責任歸屬混亂，RD 也失去主動性 → 只給限制條件（效能、相容性、資安要求），讓 RD 選做法。
- **小變更不記錄** → 五個「只是小改」累積成兩週延期，而且沒人說得清原因 → 再小的變更都進變更紀錄。

## 情境範例

電商 App 要加「以圖搜尋商品」功能，RD 估 6 週（假設值），業務希望 3 週。

- PM 問：「哪段最花時間？」RD：全品類商品圖的特徵建檔與搜尋效能約佔 4 週（假設值）。
- 拆解後的方案：第一階段只支援服飾與鞋包兩個品類、單次上傳 1 張圖，估 3 週（假設值）；其他品類與多圖搜尋放第二階段。
- 決策分工：先上哪些品類、上傳張數上限由 PM 依用戶數據決定；影像辨識模型與檢索方式的選型由 RD 決定。
- 變更紀錄：日期 ____／變更：拆成兩階段／延後：家電、美妝、多圖搜尋／RD 確認人：____。
- 對業務的回覆：「三週後先上服飾與鞋包，涵蓋目前 ____% 的搜尋流量（需查證），其他品類預計 ____ 月。」
