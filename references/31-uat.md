# 31 UAT 驗收

> 一句話：在上線前，讓真正會用這個功能的人用真實情境確認「這東西解決了原本的問題」，並把「能不能上」變成一個有依據的決定，而不是一場拖延或硬闖。

## 何時用

- 功能已經過 QA，要交給業務、客服、BU 或指定客戶確認「符合需求」再上線。
- 對外承諾過的客製需求（例如 B2B 客戶要求的專案管理 SaaS 權限流程調整），需要客戶簽核才算交付。
- 牽動既有流程的改版（帳單、權限、資料遷移），錯了會直接影響客戶工作。
- 何時不需要：純內部重構、文案微調、已用 feature flag 灰度且可秒關的小改動。這些交給 QA 加灰度監控就夠，硬開 UAT 只會拖時程。

## 動手前先問

1. **這次 UAT 要回答的問題是什麼？** 是「需求有沒有做對」還是「客戶願不願意簽收」？兩者參與者和準出條件不同。若沒答：先假設是內部需求驗證，參與者為需求提出部門。
2. **誰有權說「可以上」？** 一個人名，不是一個部門。若沒答：先假設是需求提出單位的主管，並在計畫裡標「待確認」。
3. **上線日期是硬的還是軟的？** 有沒有綁合約、活動、法規生效日？若沒答：假設是軟日期，但先寫好延期與帶病上線的決策規則。
4. **測試環境有沒有接近真實的資料？** 若沒答：假設只有測試資料，需要另外準備去識別化的範例檔與帳號。

## 做法

1. **確認準入條件，不符合就不開始。** 判斷標準：QA 的 P0／P1 缺陷已清零、測試環境穩定可用、測試帳號與資料備妥、參與者已排出時間。缺任一項就延後開跑，否則參與者會把時間花在回報環境問題，對 UAT 失去信任。
2. **從需求反推測試情境，不從功能清單排。** 每個情境要是「某角色在某狀況下要完成某件事」，例如「專案負責人在手機上把外部協作者加進專案」。判斷標準：每個 User Story 至少對應一個情境，且涵蓋主要路徑、一條常見異常路徑、一條權限或邊界情境。
3. **挑參與者。** 選實際會用的人，不是最有空的人。組合建議：1 位需求提出者（確認方向）、1–2 位一線使用者（業務／客服／客戶窗口）、必要時 1 位對法規或財務敏感的人。判斷標準：參與者能不看說明完成主要情境，才代表他們能代表真實用戶。
4. **事先公布缺陷分級規則**（見下表），並寫清楚由誰判級。PM 主持判級，RD 與需求方各有發言權，爭議時由簽核人裁定。
5. **跑 UAT 並每日收斂。** 每天固定時間過一次新缺陷：判級、指派、預計修復日。判斷標準：當天回報的缺陷，隔天站會前都有級別與負責人。
6. **對照準出條件做決定。** 只有三個選項：通過上線、延期、帶條件上線（帶病上線）。帶病上線必須同時符合：無 S1、S2 有可行的繞道方案且已告知客服、有修復日期、簽核人書面同意。
7. **書面簽核並存檔。** 簽核內容包含版本號、測試範圍、已知問題清單、修復承諾。涉及合約條款或客戶資料處理方式的變更，簽核前提醒交由法務審閱。

### 缺陷分級與處理規則

| 級別 | 定義 | 處理規則 |
|---|---|---|
| S1 阻斷 | 主要情境無法完成、資料錯誤或遺失、安全或法規風險 | 必修，未修不可上線 |
| S2 嚴重 | 主要情境可完成但需繞道，或影響特定客群 | 原則必修；帶病上線需簽核人同意 + 繞道方案 + 修復日期 |
| S3 一般 | 次要功能異常、體驗不佳但不影響結果 | 排入下一個迭代 |
| S4 建議 | 文案、樣式、新需求 | 進 Backlog，不算缺陷 |

新需求偽裝成缺陷是 UAT 最常見的拖延來源。判斷句：「規格裡有寫，做出來不一樣」才是缺陷；「規格沒寫，但我覺得應該要有」是新需求。

### 個資提醒

UAT 不要直接用正式環境的客戶資料。必須用真實資料時：取得資料來源單位同意、只匯入測試必要的欄位、姓名／Email／電話做去識別化、UAT 結束後設定刪除日期並確認執行。符合台灣個資法、GDPR、CCPA 的最小蒐集與保存期限原則。

## 品質檢查

- [ ] 簽核人是一個人名，而且這個人事前同意擔任。
- [ ] 每個測試情境都能追溯到一個需求或 User Story。
- [ ] 準出條件在 UAT 開始前就寫定，沒有在過程中被改寬。
- [ ] 缺陷分級有明確定義，且新需求已從缺陷清單分離。
- [ ] 若選擇帶病上線，已知問題清單有繞道方案、修復日期，客服已收到。
- [ ] 測試資料的來源、去識別化方式與刪除日期都有記錄。

## 常見錯誤

- **把 UAT 當第二輪 QA** → 參與者開始挑按鈕顏色、回報錯字，真正的流程問題被淹沒 → 開場就講清楚「這次只看能不能完成你的工作」，樣式問題一律標 S4。
- **準出條件事後才談** → 到了上線前一天，每個人對「夠好了」的標準不同，最後變成誰聲音大誰贏 → 準出條件寫進 UAT 計畫，開跑前請簽核人確認。
- **參與者找最有空的人** → 他們不熟實際工作，測不出真實問題，上線後一線同仁才發現流程卡住 → 寧可縮短時數，也要拿到一線使用者的 2 小時。
- **帶病上線沒有書面紀錄** → 三週後客訴進來，沒人記得當初誰同意、承諾何時修 → 已知問題清單 + 簽核人 + 修復日期，三者缺一不上。
- **UAT 無限延長** → 每修一輪就冒出新需求，上線日一直往後 → 設定 UAT 結束日，結束日當天必須在三個選項中選一個。

## 情境範例

團隊專案管理 SaaS 新增「批次邀請成員」功能，給企業客戶的 IT 管理員一次邀請 50 位新進員工加入工作區。

- 目的：確認 IT 管理員能在不看教學的情況下完成批次邀請與追蹤接受狀態。
- 簽核人：企業客戶成功部主管（姓名待填）；參與者：2 位客戶 IT 管理員、1 位內部客服。
- 情境 3：「IT 管理員上傳含 50 筆成員的 CSV，其中 2 筆 Email 格式錯誤」→ 預期系統標出錯誤列、其餘可先送出邀請。
- 結果：發現 S2 一件（錯誤列提示只顯示列號，不顯示欄位），有繞道方案（下載錯誤報告）。
- 決策：帶條件上線，S2 修復日期為上線後 2 週（假設值），客服 FAQ 已更新。
- 因涉及員工姓名與 Email 匯入，UAT 用的名單已去識別化，符合個資法規；邀請信中的服務條款若有變動，簽核前交由法務審閱。
