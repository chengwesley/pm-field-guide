# 28 資源調度

> 一句話：在人永遠不夠的前提下，讓最重要的事拿到人，並讓「不做什麼」被明確決定，而不是被默默拖掉。

## 何時用

- 新專案要啟動，需要確認誰能投入、投入多少。
- 多個專案同時要同一批人（常見是資深 RD、設計師、QA）。
- 有人請長假、離職或被臨時抽調，需要重新分配。
- 考慮外包或跨團隊借調來補人力缺口。
- 何時不需要：團隊穩定、只有一條產品線、優先級清楚的時期。照 backlog 排序做就好，不需要額外的容量盤點。

## 動手前先問

1. **這段期間公司或部門的優先順序是什麼？** 誰有權決定專案間的先後？
   若沒答：以當季 OKR 或 Roadmap 排序為準，並找出能拍板的主管名字。
2. **團隊每個人實際可用的時間是多少？**（扣掉維運、客服支援、會議、假期）
   若沒答：先假設每人可用於專案的比例為 ____%（假設值），請各 lead 修正。
3. **哪些能力只有一個人會？**
   若沒答：問各 lead「這個人請假兩週，哪些事會停」。
4. **有沒有預算或管道外包、借調？**
   若沒答：假設沒有，先在內部取捨，外包列為選項並標「需確認預算」。

## 做法

1. **盤點容量。** 以人為單位，列出未來 ____ 週（建議 4–8 週）每人的可用天數，扣除假期、維運與支援、固定會議。判斷標準：容量是「可用於專案的淨天數」，不是編制人數 × 工作天。
2. **盤點需求。** 每個專案依時程（27）列出各角色在各週需要的天數。
3. **對照找缺口。** 用「角色 × 週」的表格對照容量與需求，標出超載（需求 > 容量）的格子。判斷標準：通常缺口集中在少數關鍵角色，不是全面不足，先處理那幾格。
4. **套用取捨規則。** 事先跟主管講好規則，衝突時照規則走而不是每次重新吵：
   | 順序 | 規則 |
   |---|---|
   | 1 | 法規、資安、線上重大事故優先 |
   | 2 | 有外部承諾（合約、客戶上線日）的優先 |
   | 3 | 依當季 OKR 排序 |
   | 4 | 同一優先級時，先完成已在進行中的，減少切換 |
   每個人同時參與的專案數設上限（建議不超過 2 個），超過時切換成本會吃掉產能。
5. **處理多專案搶人。** 不要由 PM 之間私下協調，把衝突帶到有權決定的人面前，附上兩案的影響。判斷標準：決定後要寫下「誰暫停什麼、到什麼時候」，並通知被暫停專案的需求方。
6. **評估外包或借調。**
   | 適合外包 / 借調 | 不適合 |
   |---|---|
   | 範圍清楚、介面明確、可獨立驗收 | 核心邏輯、需要大量產品知識 |
   | 一次性工作（資料遷移、素材製作） | 需要長期維護的模組 |
   | 有內部人能審查品質 | 內部沒人能驗收 |
   借調時講清楚期限、回原單位的條件、誰負責考核期間的表現。涉及個資或客戶資料的外包，合約要有保密與資料處理條款，交法務審閱。
7. **處理單點故障人員。** 列出只有一人會的關鍵能力，每項安排：文件化（操作手冊、架構說明）、配對（安排第二人一起做下一次任務）、輪替（讓第二人主導、原本的人支援）。判斷標準：關鍵能力至少兩人能獨立處理。

### 向主管提出搶人衝突的話術

「____ 和 ____ 在 ____ 週同時需要 ____，她這段期間可用 ____ 天，兩邊合計需要 ____ 天。如果先給 A，B 會延 ____ 天，影響是 ____；先給 B，A 會 ____。依我們說好的規則，A 有客戶合約日期，所以我建議先給 A。請你確認，我會通知 B 的需求方。」
有效的原因：用數字說明衝突、引用事先同意的規則、給建議但把決定權交給有權的人，不會變成 PM 之間的私人角力。

## 品質檢查

- [ ] 容量是扣除維運、支援、會議、假期後的淨天數。
- [ ] 缺口標到「角色 × 週」，而不是只說「人不夠」。
- [ ] 取捨規則是事先跟決策者對齊的，不是衝突發生才想。
- [ ] 每個取捨決定都寫了被暫停的事、恢復條件、已通知對象。
- [ ] 沒有人同時參與超過約定上限的專案數。
- [ ] 單點故障人員都有對策與期限。
- [ ] 外包工作有內部驗收人，涉及個資的有保密條款。

## 常見錯誤

- **用編制人數算容量** → 「團隊有 5 個 RD」 → 實際上兩位一半時間在維運，可用只有 ____ 人。改：一律用淨天數。
- **PM 之間私下搶人** → 不想驚動主管 → 結果是誰比較強勢誰拿到人，不是誰比較重要。改：衝突上升到決策者，照規則決定，結果公開。
- **把人切成五個 20%** → 想讓每個專案都有進度 → 切換成本讓每個專案都慢。改：限制同時專案數，寧可一個暫停、一個全速。
- **外包核心模組** → 內部沒人力只好外包 → 交付後沒人看得懂、改不動。改：外包可獨立驗收的周邊工作，核心留在內部。
- **單點故障等到請假才發現** → 平常運作順利就不處理 → 關鍵人員一請假，上線卡住。改：每季檢查一次單點故障清單，排配對任務。

## 情境範例

電商 App 與商家後台第 ____ 季資源調度（數字皆為假設值）：

- 資深 RD 小 A（前端與 iOS 都能做）：4 週可用淨天數 14 天（扣除維運 4 天、假期 2 天）。
- 需求：商家後台「批次上架商品」10 天、電商 App iOS 新版相容修正 8 天，合計 18 天，缺口 4 天。
- 規則：iOS 新版相容有平台更新時程（外部時間），優先。
- 決定：小 A 先做相容修正 8 天，批次上架只給 6 天，先支援 CSV 匯入，Excel 匯入延到下一版。恢復條件：相容修正上線後。決策者：____。已通知商家後台需求方與商家營運。
- 單點故障：商品匯入與規格對應模組只有小 A 熟悉 → 安排小 B 配對參與這次開發，____ 前寫好架構說明。
