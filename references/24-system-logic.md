# 24 系統邏輯

> 一句話：把散落在 PM 腦中的「如果……就……」寫成狀態、權限、規則三張表，讓 RD 不用猜、QA 不會漏、客服答得出來。

## 何時用

- 功能有生命週期（草稿 → 送出 → 處理中 → 完成 / 失敗 / 取消），而且不同狀態下能做的事不一樣。
- 有多種角色、方案或權限層級，同一個按鈕對不同人有不同結果。
- 規則有三個以上條件交叉（方案 × 角色 × 狀態），用文字段落一定會漏組合。
- 上線後客服常收到「為什麼我不能 ____」，代表規則沒被寫清楚。
- 何時不需要：單一狀態、單一角色、無分支的功能（例如純顯示頁）。寫幾條驗收條件就夠。

## 動手前先問

1. **這個物件有哪些狀態？誰或什麼事件會讓它改變？**
   若沒答：先從使用者旅程列出「名詞 + 形容詞」（訂單：待付款、已付款、已取消），再請 RD 對照現有資料庫的狀態欄位。
2. **有哪些角色與方案？誰可以對什麼做什麼？**
   若沒答：從現有產品的角色設定抄一份，標「沿用現況，待確認是否需新增」。
3. **規則衝突時誰優先？**（例如管理員設定 vs 個人設定、方案限制 vs 合約特例）
   若沒答：預設「越嚴格的優先、合約特例由後台設定覆蓋」，列為未決事項。
4. **哪些狀態轉移不可逆？**
   若沒答：假設「已完成」與「已刪除」不可逆，其他可逆，請 RD 與法務確認。

## 做法

1. **畫狀態機。** 列出所有狀態，每個狀態寫一句定義（進入條件）。判斷標準：任一時間點，一筆資料只能屬於一個狀態；如果出現「既是 A 又是 B」，代表狀態要拆或要改成兩個獨立欄位。
2. **填狀態轉移表。** 每一列 = 從哪個狀態、被什麼事件觸發、要滿足什麼條件、轉到哪個狀態、附帶什麼副作用（通知、記錄、扣額度）。接著做「空格檢查」：把所有狀態 × 所有事件排成矩陣，每格要嘛有轉移，要嘛明寫「不允許，回應 ____」。空格就是 bug 的來源。
3. **做權限矩陣。** 列 = 動作，欄 = 角色（必要時再加方案維度）。每格填 ✓ / ✗ / 條件（例如「僅限自己建立的」）。判斷標準：每個 ✗ 都要寫使用者會看到什麼（隱藏、灰掉、點了跳提示）。
4. **整理業務規則表。** 每條規則一個編號（BR-01），寫規則、適用範圍、數值、例外、來源（誰決定的、合約或法規依據）。數值只在這裡定義一次，其他文件引用編號。
5. **條件交叉時用決策表。** 列出所有條件與可能值，展開組合，每組合對應一個結果。組合太多時先合併「結果相同」的列，用「-」表示不影響。判斷標準：組合數 = 各條件值數相乘，表格行數要對得上（或明寫合併理由）。
6. **列邊界與衝突案例。** 專門找這幾類：同時操作（兩人同時改）、時間（剛好在到期那一秒、跨時區）、順序（先取消再退款）、外部失敗（通知寄不出去）、資料殘留（刪除角色後他建立的東西怎麼辦）。每個案例寫預期行為。
7. **跟 RD 對一次。** 拿轉移表問「現在的程式碼哪些轉移是允許的？」常會發現系統允許但規格沒寫的路徑。

## 品質檢查

- [ ] 每個狀態有一句可判斷的定義，且不存在同時屬於兩個狀態的情況。
- [ ] 狀態 × 事件矩陣沒有空格，「不允許」的格子都有回應文案或行為。
- [ ] 終態有明確標示，且寫了終態之後還能做什麼（檢視、下載、複製）。
- [ ] 權限矩陣每個 ✗ 都寫了呈現方式（隱藏 / 灰掉 / 提示）。
- [ ] 規則數值只在業務規則表出現一次，其他文件引用編號。
- [ ] 決策表行數對得上條件組合數，或寫明合併理由。
- [ ] 邊界案例至少涵蓋併發、時間、順序、外部失敗四類。

## 常見錯誤

- **用段落描述狀態** → 寫「訂單送出後，若店家接單就備餐，若逾時則……」 → 讀的人自己腦補沒寫到的轉移。改：一律用轉移表，再做空格檢查。
- **狀態跟屬性混在一起** → 把「已封存」「已加星號」也當狀態 → 一筆資料同時是「已完成」又「已封存」，狀態機爆炸。改：狀態只描述生命週期，其他用獨立欄位（見 26）。
- **只寫允許的，不寫禁止時怎麼辦** → 覺得「不能做」就是不用寫 → RD 各自決定隱藏或報錯，前後端不一致。改：每個禁止都寫使用者看到什麼。
- **忽略時間與時區** → 「7 天後過期」沒寫起算點與時區 → 跨國客戶抱怨提早或延後過期。改：寫清楚起算事件、精度（日或秒）、以哪個時區計算。
- **規則來源沒記** → 不知道某條規則是法規要求還是某次會議隨口定的 → 之後沒人敢改或隨便改。改：業務規則表加「來源 / 決定者」欄。

## 情境範例

以下以外送平台的訂單為例，**僅為說明方法的示意，非任何實際產品的狀態設計或規則**。

| # | 從 | 事件 | 條件 | 到 | 副作用 |
|---|---|---|---|---|---|
| T1 | 待付款 | 顧客完成付款 | 付款授權成功、店家營業中 | 待接單 | 通知店家 |
| T2 | 待接單 | 店家接單 | 尚未超過接單時限 | 備餐中 | 通知顧客、開始派單 |
| T3 | 待接單 | 店家拒單 | — | 已取消 | 通知顧客、取消付款授權 |
| T4 | 待接單 | 系統排程 | 超過接單時限 ____ 分鐘（假設值，以伺服器時間計） | 逾時取消 | 通知顧客與店家、取消付款授權 |
| T5 | 待接單 | 顧客取消 | 店家尚未接單 | 已取消 | 通知店家、取消付款授權 |

- 衝突案例 E3：顧客取消與店家接單在同一秒發生，以伺服器先寫入者為準，另一方收到「訂單狀態已變更」提示。
- 提醒：涉及取消費用、退款與消費爭議的規則，產出前務必交由法務審閱，不可直接當作對外條款依據；訂單含顧客地址與外送員位置，保存期限與存取權限要符合個資法規。
