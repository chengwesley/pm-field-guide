# 19 A/B 測試

> 一句話：用隨機分組比較兩個版本，在事前寫定的規則下判斷改動是否真的造成差異，而不是看到想看的數字就下結論。

## 何時用

- 兩個版本都合理，團隊爭論不下，而且流量足夠在合理時間內得到結果。
- 改動可能有副作用（例如提升註冊但傷害付費），需要同時看主指標與護欄指標。
- 要量化一個改動的效果大小，作為後續投資的依據。
- 何時不能（或不該）做 A/B：流量太小，算出來要跑好幾個月；改動牽涉法律、隱私或合約條款，不能讓部分用戶得到不同待遇；改動會被用戶互相看到並影響彼此（例如多人協作，或買賣雙方都會看到的流程）；改的是品牌或整體方向，短期指標反映不出來；或修 bug、合規要求這種本來就必須做的事。

## 動手前先問

1. **假設是什麼？預期往哪個方向、變多少？** 若沒答：先寫一個草案（「改 X 會讓 Y 從 ____ 到 ____」），請對方確認最小有意義的變化量。
2. **主指標與護欄指標各是什麼？** 若沒答：主指標用最接近價值的轉換，護欄至少包含營收相關、錯誤率、取消或退款。
3. **每天有多少符合條件的用戶進入實驗？目前的基準轉換是多少？** 若沒答：無法算樣本數，先去取數，不要先開跑。
4. **以什麼單位隨機？** 若沒答：預設以用戶（帳號）隨機，避免同一人看到兩個版本。

## 做法

1. **寫假設。** 「因為 ____（觀察），我們相信改 ____ 會讓 ____（對象）的 ____（主指標）提升至少 ____（最小可偵測效果）。」判斷標準：有方向、有幅度、有依據。
2. **選一個主指標，加護欄指標。** 主指標只能一個，用來做決定；護欄指標用來否決。判斷標準：結果出來前就寫好「主指標達標但護欄變差多少就不上線」。
3. **事前計算樣本數與時長。** 用基準轉換率、最小可偵測效果、顯著水準（常用 5%）與檢定力（常用 80%）算出每組所需人數，再除以每日流量得出天數。判斷標準：
   - 時長至少涵蓋完整週期（通常至少一到兩週），避免平日假日差異。
   - 算出來太久（例如超過 ____ 週，假設值），回頭調整：放大改動幅度、換更靠前的指標，或不做 A/B。
   - 樣本數與停止日寫進文件，開跑後不改。
4. **檢查實驗健康度。** 開跑後一兩天內確認分流比例是否符合設定（樣本比例不符代表分流或埋點有問題）、兩組事件是否都正常記錄。判斷標準：分流比例明顯偏離時暫停查原因，這不算「提早看結果」。
5. **不可看到顯著就提早停。** 每天看 p 值、一顯著就停，會大幅提高誤判機率。判斷標準：只在事前約定的停止日判讀；若真的需要中途看，事前就採用序列檢定等允許中途判讀的方法並寫清楚規則。唯一可以提前停的理由是護欄指標出現嚴重傷害。
6. **處理多重比較。** 同時看很多指標、很多分群、很多變體時，總會有某個剛好顯著。判斷標準：決策只看事前定的主指標；分群結果標為「探索性」，要另開實驗驗證；多變體時調整顯著水準（例如 Bonferroni）或減少變體數。
7. **留意新奇效應與學習效應。** 新版本一開始可能因為新鮮而表現好，或因為不熟悉而表現差。判斷標準：把結果按天或按新舊用戶拆開看，若差距隨時間明顯縮小或擴大，延長觀察或只看新用戶。
8. **判讀與決策。** 回報效果大小與信賴區間，不只是「顯著／不顯著」。判斷標準：不顯著不等於沒效果，可能是樣本不夠；寫明「依事前規則，決定上線／不上線／重新設計」。

## 品質檢查

- [ ] 假設有方向、幅度與依據。
- [ ] 只有一個主指標，護欄指標的否決門檻事前寫定。
- [ ] 樣本數、停止日在開跑前算好並記錄，且時長涵蓋完整週期。
- [ ] 有檢查分流比例與埋點健康度。
- [ ] 判讀日就是事前寫定的停止日，沒有提早停。
- [ ] 分群與次要指標標成探索性，沒有拿來當上線理由。
- [ ] 回報包含效果大小與信賴區間。

## 常見錯誤

- **看到顯著就停** → 老闆每天問結果，綠色數字出現時很想宣布 → 停止日寫進計畫並在開跑會議上講清楚，儀表板上不顯示每日 p 值或標註「未到判讀日」。
- **跑完再挑一個好看的指標** → 主指標沒顯著，但某個次要指標有 → 主指標事前定，其他結果只能當下一輪的假設。
- **流量不夠還硬做** → 覺得 A/B 比較科學 → 先算樣本數；要跑太久就改用易用性測試、分批上線觀察或直接依判斷決定。
- **分群挖到「某群效果很好」就只對那群上線** → 分群越多越容易碰巧顯著 → 把它當新假設，針對那群另開一次實驗。
- **忽略新奇效應** → 前三天效果最大，報告就用那時的數字 → 按時間拆開看效果趨勢，必要時延長或只看新用戶。
- **在雙方互動的流程做 A/B** → 沒想到買方與賣方會看到不同版本 → 以組織或訂單為隨機單位，或改用其他驗證方式。

## 情境範例

健身訂閱 App 付費牆：測試把「年繳方案」設為預設選項。
- 假設：因為多數付費用戶事後改為年繳（需查證），把年繳設為預設會讓付費轉換中的年繳比例提升至少 ____ 個百分點。
- 主指標：年繳佔付費比例。護欄：整體付費轉換率（惡化超過 ____ 否決）、14 天內退款率。
- 基準與流量：每日進入付費牆 ____ 人，算出每組需 ____ 人、約 ____ 天（假設值），停止日 ____。
- 隨機單位：帳號，避免同一人在手機與平板看到不同版本。
- 第 4 天 B 組顯著領先，依計畫不停止；第 14 天判讀：主指標提升 ____，護欄未惡化（假設值）。
- 決定：上線，30 天後複查退款率。
- 本實驗涉及定價呈現與自動續訂說明，對外使用前需經相關主管審閱。

## 工具

- 設計階段：`scripts/ab_test.py size --baseline <基準轉換率> --mde <最小可偵測差異> --daily-traffic <每日流量>`，算每組樣本數與天數；超過兩組時自動做 Bonferroni 校正。
- 判讀階段：`scripts/ab_test.py analyze 結果.csv --planned-n <每組預計樣本數>`，算顯著性與信賴區間，先檢查樣本比例失衡（SRM），樣本還沒到預計數量時提醒不要提早下結論。
