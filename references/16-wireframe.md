# 16 Wireframe

> 一句話：在花時間做視覺之前，用低保真畫面先對齊「這頁放什麼、什麼最重要、點了會怎樣」。

## 何時用

- PRD 的需求寫完了，要跟設計師對齊頁面該有哪些內容與優先順序。
- 有兩三種版面做法，想快速比較再決定。
- RD 想先開始做後端，需要知道畫面會用到哪些資料。
- 何時不需要：設計師已經有成熟的設計系統，而且改動只是在既有元件上換文案；或你想驗證的是動態互動，那改做 Prototype。

## 動手前先問

1. **這個畫面要讓用戶完成什麼？** 若沒答：從 User Flow 對應的步驟抓主要動作，先假設一頁只有一個主要動作。
2. **畫面上的資料從哪來？有沒有可能是空的、很長的、很多筆的？** 若沒答：預設每個欄位都要考慮空值、超長、大量三種情況。
3. **由誰畫？PM 畫到哪裡為止？** 若沒答：假設 PM 畫「內容與優先順序」的草圖，版面細節由設計師決定。
4. **要支援哪些裝置尺寸？** 若沒答：先畫最受限的那個（通常是手機），再擴展。

## 做法

1. **列內容清單，排優先順序。** 寫下這頁所有要出現的資訊與動作，標「必要／重要／次要」。判斷標準：「必要」不超過 3–5 項；如果每個都是必要，代表還沒做取捨。
2. **決定主要動作。** 一頁一個主要動作，其他是次要。判斷標準：遮住所有文字，只看框的大小與位置，能猜出主要動作在哪。
3. **畫低保真。** 灰階、方框、真實或接近真實的文案，不用顏色、圖示、字型。判斷標準：別人看了會評論「內容與順序」，而不是「這個藍色太亮」。
4. **用真實資料長度。** 帶入最長的名稱、最多筆的清單、空的狀態。判斷標準：每個區塊都測過空、一筆、很多筆三種。
5. **加標註。** 每個互動元素用編號標註，對應到下方說明表。判斷標準：RD 不看你本人解說，只看標註就知道點了之後去哪、呼叫什麼資料、什麼條件下隱藏。
   | 標註要寫 | 不必寫 |
   |---|---|
   | 點擊後行為、顯示／隱藏條件、資料來源、字數上限、錯誤狀態 | 顏色、間距、字型大小（交給設計） |
6. **與設計師對齊。** 交付時講清楚「這是內容與優先順序的提案，版面歡迎推翻」。判斷標準：設計師提出的改法能回應同樣的內容優先順序，就接受；改了優先順序的部分要一起討論原因。
7. **版本管理。** 每次改動記錄日期與原因，標記哪一版是開發依據。判斷標準：不會出現 RD 照著舊版做的情況。

## 品質檢查

- [ ] 每頁只有一個主要動作，遮住文字也看得出來。
- [ ] 「必要」內容不超過 3–5 項。
- [ ] 每個區塊都畫過空、一筆、很多筆的情況。
- [ ] 每個互動元素都有編號標註，寫明行為與條件。
- [ ] 沒有花時間在顏色、圖示、字型上。
- [ ] 明確標出哪些部分開放設計師決定。
- [ ] 有版本號與開發依據版本。

## 常見錯誤

- **Wireframe 畫得太精緻** → PM 想展現誠意或直接拿去給老闆看 → 保持灰階方框，討論才會聚焦在內容；要給老闆看就另外說明「這是結構不是設計」。
- **用 Lorem ipsum 假文字** → 還沒想好文案 → 至少寫接近真實長度的文案，假文字會掩蓋版面撐破的問題。
- **PM 畫完版面就當定案** → 想加快速度 → 把 Wireframe 定位為「內容與優先順序」的提案，版面讓設計師主導。
- **標註只寫「點了跳轉」** → 覺得 RD 會懂 → 寫清楚跳到哪、帶什麼參數、什麼條件下不能點。
- **只畫有資料的漂亮狀態** → 示意最好看 → 固定附上空狀態與錯誤狀態。

## 情境範例

健身 App 新增「本週課表總覽」頁（手機版先畫）。
- 主要動作：開始今天的訓練。
- 必要：本週七天課表、開始今天的訓練、每堂課完成狀態。重要：本週完成進度。次要：排序、分享。
- 標註 #1「開始今天的訓練」：點擊後進入暖身說明；今天是休息日時改為顯示明天的課；免費方案每週可排課數達上限（假設值 ____ 堂）時改為顯示升級說明。
- 標註 #2 課程卡片：課程名稱超過 20 字（假設值）截斷並加「…」，長按顯示完整名稱與「改到別天」。
- 空狀態：第一次使用還沒排課，顯示一份入門課表範例與「從這裡開始」說明。
- 開放給設計決定：一週用橫向日曆或直式清單呈現。
- 變更紀錄：v2 把「分享」從主畫面移到長按選單，原因是使用頻率低（假設值）。
