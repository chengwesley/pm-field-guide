# 18 易用性測試

> 一句話：看真實用戶在沒有協助的情況下操作產品，找出哪些地方會讓人卡住，並依嚴重程度決定先修什麼。

## 何時用

- 新流程或改版上線前，想知道用戶能不能自己完成。
- 漏斗分析顯示某一步流失多，判讀為「不會做」，需要看到具體卡在哪。
- 團隊對某個設計爭論不休，需要用戶行為來決定。
- 何時不需要：要回答「用戶想不想要」或「願意付多少」，那是需求或定價研究；要比較兩個方案哪個轉換高，且流量足夠，用 A/B 測試。

## 動手前先問

1. **要驗證哪些任務？** 若沒答：從 User Flow 的主流程與最大漏損點挑 3–5 個任務。
2. **受測者是誰？怎麼招募？** 若沒答：假設招募符合目標用戶輪廓、但沒用過這個功能的人，並排除公司同事。
3. **現場、遠端、有主持還是無主持？** 若沒答：預設遠端有主持，便於追問。
4. **測試結果誰來看、會影響哪個決定？** 若沒答：假設影響上線前的修正清單，請相關設計師與 RD 至少觀看 2 場。

## 做法

1. **寫任務，不寫指令。** 任務描述情境與目標，不提介面用詞。判斷標準：任務句子裡沒有出現介面上的按鈕名稱。
   | 不好 | 好 |
   |---|---|
   | 「請點『新增品項』並上傳照片」 | 「你的店下週要開賣一道新便當，請用這個工具讓客人點得到」 |
2. **定成功標準。** 每個任務事前定義怎樣算完成、怎樣算有協助完成、時間上限。判斷標準：兩位觀察者對同一場的判定一致。
3. **決定人數，並理解 5 人原則的限制。** 常見的「5 人就能發現大部分問題」適用於：同一群用戶、同一組任務、目標是找問題而非量化。不適用的情況：
   - 有明顯不同的用戶群（個人 vs 企業管理員）→ 每群各測一輪。
   - 要估計完成率或比較兩個方案 → 需要更多人，屬於量化測試。
   - 問題出現機率很低（只有少數人會遇到）→ 5 人很可能看不到。
   判斷標準：先說明這輪要「找問題」還是「量化」，再決定人數；找問題傾向小樣本多輪，改了再測。
4. **執行。** 開場說明「我們在測產品，不是測你」，請受測者邊做邊說。主持人不提示，被問時反問「你覺得呢？」。判斷標準：主持人說的話遠少於受測者。
5. **記錄觀察，不記意見。** 記「做了什麼、在哪裡停頓、說了什麼」，用戶說「我覺得很好用」不等於好用。判斷標準：每條紀錄都有時間點與具體行為。
6. **分級嚴重度。**
   | 等級 | 定義 | 處置 |
   |---|---|---|
   | 嚴重 | 無法完成任務，或會造成資料錯誤、法律風險 | 上線前必修 |
   | 重大 | 能完成但明顯困擾、花很多時間或需要猜 | 優先修 |
   | 輕微 | 小停頓，自己很快排除 | 排入待辦 |
   | 建議 | 用戶提出的偏好，不影響完成 | 記錄參考 |
   判斷標準：嚴重度看「影響」與「出現頻率」，不看受測者語氣有多強烈。
7. **判讀與回報。** 合併同一問題，寫成「問題 → 證據（幾人、哪一場）→ 嚴重度 → 建議方向」。判斷標準：建議寫方向而不是解法細節，解法交給設計討論。

### 錄影錄音與個資提醒

- **事前取得書面同意**：說明錄什麼（畫面、聲音、臉）、用途、誰會看、保存多久，以及可隨時停止。
- **最小蒐集**：只錄任務需要的畫面；請受測者使用測試帳號與假資料，避免螢幕出現真實訂單、對話或通知。
- **去識別化**：報告與剪輯片段不放姓名、臉部特寫或聯絡資訊，以代號稱呼（P1、P2）。
- **保存與刪除**：設定保存期限（例如 ____ 個月），到期刪除；存放位置限團隊存取。跨境受測者適用 GDPR／CCPA 時，同意書與存放地點請與法務確認。

## 品質檢查

- [ ] 任務描述沒有洩漏介面用詞。
- [ ] 每個任務有事前定義的成功標準。
- [ ] 說明了這輪是找問題還是量化，人數選擇有理由。
- [ ] 紀錄的是行為與時間點，不是受測者的評價。
- [ ] 每個問題都有嚴重度與出現人數。
- [ ] 錄影錄音有書面同意、保存期限與刪除負責人。

## 常見錯誤

- **任務寫成操作指令** → 想確保受測者走到要測的地方 → 改寫成情境，走不到本身就是發現。
- **主持人忍不住幫忙** → 看到受測者卡住會尷尬 → 事前約定「除非完全卡死超過 ____ 分鐘，否則不提示」，提示了就記為協助完成。
- **用 5 個人宣稱完成率** → 5 人原則被當成通用定律 → 小樣本只報「幾人中幾人」，不換算成百分比。
- **把受測者的意見當結論** → 「用戶說想要深色模式」比較好寫 → 意見放「建議」等級，結論以行為為主。
- **測完只交一份長報告** → 想展現完整 → 先開 30 分鐘會播 3 段關鍵片段，現場對齊嚴重問題的處置。

## 情境範例

外送平台店家端新版「上架菜單」流程，上線前測試。
- 目的：找問題。受測者：過去 3 個月內在其他點餐系統上架過菜單、但沒用過本平台店家端的餐飲店家 5 人（假設值）。
- 任務 1：「店裡下週起新增一道雞腿便當，加滷蛋要多收 15 元（假設值），請用手機把它上架並開始販售。」成功標準：品項出現在正確分類、加購價格正確且成功上架，時間上限 5 分鐘。
- 結果：完成 2、協助完成 2、失敗 1（假設值）。
- 問題：4/5 在新增加購選項時找不到「必選／可選」設定（重大）；1/5 把價格填進「原價」欄，售價變成 0 元且未察覺就上架（嚴重，會造成錯誤收款）。
- 建議方向：上架前顯示品項、分類與價格的摘要確認；必選／可選設定移到加購選項旁。
- 同意書已簽，錄影保存 ____ 個月後刪除；錄影避免拍到店家真實營收與顧客訂單資料。價格與抽成相關的說明文字，對外使用前需經相關主管審閱。
