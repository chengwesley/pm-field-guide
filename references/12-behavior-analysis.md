# 12 行為分析

> 一句話：看清楚用戶「實際怎麼用」產品，而不是他們說自己怎麼用，並把觀察變成可以行動的判斷。

## 何時用

- 新功能上線一個月，使用率不如預期，想知道是沒人發現、用了不會、還是用了不想再用。
- 準備規劃埋點，要先決定該記哪些事件、怎麼命名，免得半年後資料沒法用。
- 想知道哪一群用戶留下來、哪一群流失，以及兩群在前幾天做了什麼不一樣的事。
- 何時不需要：已經知道問題是在某個多步驟轉換掉人，直接用 `13-funnel-analysis.md`；樣本只有十幾個人，用訪談比看數據快。

## 動手前先問

1. **你想做什麼決策？**（要不要砍功能、要不要改 onboarding）若沒答：先假設是「判斷某功能值不值得繼續投入」，並據此挑指標。
2. **現在有哪些事件已經在記？命名規則是什麼？** 若沒答：假設既有資料不可信，先抽 3 個關鍵事件檢查是否與實際操作一致。
3. **「活躍」怎麼定義？** 若沒答：先用「完成核心動作」而不是「打開 App」來定義，並請對方確認核心動作是什麼。
4. **有沒有定性資料可以搭配？**（客服單、訪談、評論）若沒答：假設沒有，在計畫裡排 5 通（假設值）用戶訪談。

## 做法

1. **從決策倒推問題。** 寫下「如果看到 A 我們就做 X，看到 B 就做 Y」。判斷標準：每個要看的數字都對應到一個會改變的行動；對應不到的先不看。
2. **設計事件與命名。** 用「物件_動作」的過去式（`item_added`、`checkout_completed`），屬性放在 properties 而不是塞進事件名。判斷標準：
   | 好 | 不好 | 為什麼 |
   |---|---|---|
   | `item_shared` + `channel: email` | `share_email_click` | 管道放屬性，之後新增管道不用改事件 |
   | `checkout_completed` | `btn_done_click` | 記「結果」而不只是「點擊」 |
   | 全部小寫底線 | 大小寫混用 | 查詢時不會漏算 |
   另外寫一份事件字典：事件名、觸發時機、屬性、負責人、上線日期。
3. **驗證資料。** 在測試環境自己操作一遍，對照事件是否只觸發一次、時間戳正確、屬性有值。判斷標準：手動操作 10 次，事件數也是 10。
4. **分群。** 先用行為分群（例如「第一週有完成核心動作 vs 沒有」），再用屬性分群（方案、平台、來源）。判斷標準：每一群至少要有足夠人數讓差異不是雜訊，人太少的群合併或標註「僅供參考」。
5. **看留存與 cohort。** 以「首次使用日」或「首次完成核心動作日」分批，看第 1、7、30 天回訪。判斷標準：比較的是同期 cohort 的曲線形狀，而不是全體平均；曲線有沒有在某一天後變平，比絕對值更重要。
6. **找差異行為。** 比較留存好與留存差的兩群，在前 N 天做了哪些不同的事。判斷標準：這只是相關，標成「候選假設」，要用實驗或訪談驗證才能說是原因。
7. **用定性補「為什麼」。** 從數據挑出代表性用戶（行為異常、高度使用、剛流失）去訪談或看客服紀錄。判斷標準：每一條結論都能說出「數據看到什麼」＋「用戶說了什麼」。

### 個資實務提醒

- **告知與同意**：埋點與第三方分析工具要在隱私權政策中說明蒐集目的；GDPR 適用地區的非必要追蹤需事先取得同意，CCPA 需提供選擇退出機制。
- **最小蒐集**：事件屬性不放 email、姓名、用戶輸入的文字或上傳內容；用內部 user_id。
- **去識別化**：匯出分析或分享給外部時，移除或雜湊識別欄位；小樣本分群要注意能否反推到個人。
- **保存期限**：原始事件設定保存期間（例如 ____ 個月），到期刪除或彙總。具體規則請與法務／資安確認。

## 品質檢查

- [ ] 開頭寫了要做的決策，而且每個指標都對應到一個行動。
- [ ] 事件名稱一致、記的是結果而不是只有點擊，且有事件字典。
- [ ] 資料有經過手動操作驗證，不是直接相信儀表板。
- [ ] 留存用 cohort 比較，不是拿全體平均跨時間比。
- [ ] 每個「差異行為」都標成假設，沒有直接寫成因果。
- [ ] 至少一條結論有定性資料佐證。
- [ ] 事件屬性沒有個資，保存期限有寫。

## 常見錯誤

- **先埋一堆事件，之後再想要看什麼** → 怕漏記，結果事件幾百個沒人敢用 → 每個事件上線前要寫它服務的決策，寫不出來就不埋。
- **把「打開 App」當活躍** → 最容易量 → 用核心價值動作定義活躍，例如電商是「完成一次下單」。
- **看到「用了 X 功能的人留存比較高」就推廣 X** → 會主動用進階功能的人本來就比較投入 → 標成相關，用 A/B 或分批釋出驗證。
- **改版後事件名改了，歷史資料斷掉** → RD 順手重構 → 事件字典列入 code review 檢查項，改名要寫對照表與切換日。
- **只看數據不聯絡用戶** → 覺得訪談慢 → 從數據挑 3–5 個極端案例直接聊，通常半天就能補上「為什麼」。

## 情境範例

電商新增「AI 商品比較」一個月，使用率低於預期（假設值：週活躍用戶中 ____% 用過）。
- 決策：要繼續優化入口，還是降低投入。規則：若「看過入口但沒點」佔多數 → 改文案；若「點了但沒完成」佔多數 → 改流程。
- 事件：`ai_compare_entry_viewed`、`ai_compare_requested`、`ai_compare_completed`（屬性：`item_count`、`category`、`platform`）。
- 驗證：測試機操作 10 次，發現 `entry_viewed` 在商品列表滾動時重複觸發，先修正再看數據。
- 分群：第一週用過 AI 商品比較 vs 沒用過，D30 留存差 ____ 個百分點（假設值）——標為相關，不是因果。
- 定性：訪談 5 位用過一次就沒再用的人，3 位（假設值）說比較結果太長、抓的規格不是自己在意的。
- 個資：屬性不記會員姓名、收件地址與搜尋原文。
