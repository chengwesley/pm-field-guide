# 43 UIUX 協作

> 一句話：給設計師問題與限制，而不是畫好的答案；評稿時講對使用者的影響，交付時確認工程拿到的是做得出來的東西。

## 何時用

- 新功能要請設計師出稿，你準備寫設計需求。
- 設計稿出來了，你要給回饋。
- 設計稿要交給 RD 前，確認交付完整。
- 上線後的畫面跟設計稿不一樣，要處理落差。

何時不需要：純文案微調、沿用既有元件的小改動（直接在設計系統內處理，知會設計師即可）。

## 動手前先問

1. **使用者是誰、在什麼情境下用到這個畫面？** 若沒答：先用現有用戶研究或客服工單推一個主要情境，標「待驗證」。
2. **這次設計要改善的指標是什麼？** 若沒答：先假設是該流程的完成率，並請設計師一起確認。
3. **有哪些限制？** 平台（Web／iOS／Android）、既有元件、技術限制、法規文字（例如個資蒐集的同意聲明）。若沒答：預設要沿用設計系統，偏離要說明理由。
4. **設計要到什麼保真度？探索方向還是可交付？** 若沒答：先假設第一輪是方向探索，不要一開始就要求精稿。

## 做法

1. **寫設計需求時給問題，不給解法。** 判斷標準：需求裡出現「加一個按鈕在右上角」這類描述，就是在給解法。改成「使用者在 ____ 時找不到 ____，導致 ____」。你腦中有畫面可以附，但標明「僅供參考，不是要求」。
2. **第一輪要多方向。** 請設計師給 2–3 個方向，而不是一個精稿。判斷標準：方向之間要有真正的差異（流程不同、資訊層級不同），不是只換顏色。
3. **評稿回饋用「觀察 → 影響 → 問題」寫。**
   - 觀察：「結帳按鈕在首屏看不到」
   - 影響：「手機使用者可能不知道下一步，我們目前的完成率是 ____（假設值）」
   - 問題：「有沒有辦法讓下一步在首屏就看得到？」

   判斷標準：回饋裡沒有「我覺得不好看」「改成藍色」這類個人偏好或指定解法。視覺偏好交給設計師判斷。
4. **把回饋分級。** 每條標上：必改（影響任務完成或法規）、建議（影響體驗但不阻斷）、討論（PM 不確定，想聽設計師想法）。避免設計師把所有意見都當必改。
5. **交付前跑檢查表。**

   | 項目 | 確認 |
   |---|---|
   | 狀態 | 空狀態、載入中、錯誤、成功、無權限都有畫 |
   | 尺寸 | 各斷點或裝置尺寸 |
   | 文案 | 最終文案（含多語系長度最長的版本） |
   | 互動 | 動效、轉場、hover、點擊區域 |
   | 元件 | 標明哪些用設計系統、哪些是新元件 |
   | 標註 | 間距、字級、顏色 token 可被 RD 取用 |

6. **處理設計與工程落差。** 開發中期安排一次設計師看實機。落差分三類：做錯了（照稿修）、做不到（設計師與 RD 一起找替代）、稿沒畫（補稿）。判斷標準：每個落差都有歸類與負責人，不是「上線後再說」。
7. **善用設計系統。** 新需求先問「現有元件能不能解」。真的需要新元件，請設計師評估是否該進設計系統，而不是只做給這一頁。

## 產出模板

```markdown
### 設計需求單
- 功能／頁面：____
- 主要使用者與情境：____
- 要解決的問題：使用者在 ____ 時，因為 ____，所以 ____
- 成功指標：____（目前 ____，目標 ____，假設值）
- 限制：平台 ____／技術 ____／法規文字 ____／需沿用元件 ____
- 這次不處理：____
- 參考（非要求）：____
- 本輪保真度：方向探索／中保真／可交付
- 評稿日期：____

### 評稿回饋
| # | 畫面 | 觀察 | 對使用者的影響 | 問題／建議 | 等級（必改／建議／討論） |
|---|---|---|---|---|---|
| 1 | ____ | ____ | ____ | ____ | ____ |
```

### 話術

- 想推翻一個方向時：「這個方向在 ____ 情境下很好，但我們最主要的使用者是 ____，他們會卡在 ____。你覺得要怎麼兼顧？」——把問題交回設計師，而不是自己提新解法。
- 不同意但沒把握時：「這點我不確定，可以用 ____ 個使用者快速測一下嗎？」——用驗證取代爭論誰對。
- 設計師堅持但成本高時：「這個效果 RD 估要 ____ 天。它對 ____ 指標的幫助有多大？如果不確定，我們先上簡化版，看數據再決定。」

## 品質檢查

- [ ] 設計需求單裡沒有指定版面位置、顏色、元件形式的語句（除非是法規或設計系統限制）
- [ ] 第一輪有 2 個以上真正不同的方向
- [ ] 每條評稿回饋都寫了對使用者的影響
- [ ] 每條回饋都有等級標示
- [ ] 交付檢查表的狀態欄（空、載入、錯誤、無權限）全部有稿
- [ ] 實機落差都有歸類與負責人
- [ ] 新元件已評估是否進設計系統

## 常見錯誤

- **PM 自己畫好 wireframe 叫設計師「美化」** → 設計師只能在你的框架內調整，錯過更好的解法，也會失去投入感 → 給問題與限制，wireframe 只當溝通輔助並標明可以推翻。
- **評稿時講個人喜好** → 「我不喜歡這個顏色」讓設計師無所適從，也削弱你其他回饋的份量 → 只講對任務完成與指標的影響。
- **回饋分散在 Slack、會議、口頭** → 設計師漏改，PM 以為講過了 → 集中在設計檔的評論或一張回饋表。
- **只看 happy path** → 錯誤狀態、空狀態沒畫，RD 自己發揮，上線後畫面不一致 → 交付檢查表的狀態欄一個都不能少。
- **上線後才發現跟稿不一樣** → 修改成本最高的時間點 → 開發中期就安排設計師看實機。

## 情境範例

線上課程 App 要改善「離線下載」流程，客服反映使用者不知道下載進度。

- 設計需求單問題句：使用者在下載整門課程時，因為看不到進度與剩餘時間，所以重複點擊或關閉 App，導致下載失敗。
- 成功指標：下載成功率從 ____ 到 ____（假設值）；相關客服工單減少。
- 限制：iOS 與 Android 的手機、平板都要支援；下載中 App 切到背景、網路從 Wi-Fi 切到行動網路的情況要處理。
- 評稿回饋範例：觀察「進度條只有百分比」／影響「下載整門課時使用者無法判斷要等多久」／問題「有沒有辦法給預估時間或可以先去看已下載單元的提示？」／等級：建議。
- 交付檢查補到的狀態：下載失敗、裝置空間不足、課程授權到期、切到背景後回來。
