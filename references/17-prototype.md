# 17 Prototype

> 一句話：用最低的成本做出「夠真」的可操作模型，在投入開發前驗證一個明確的假設。

## 何時用

- 有一個高風險的互動設計（新的手勢、新的編輯方式），寫在文件上沒人能判斷好不好用。
- 要在開發前做易用性測試，需要讓受測者真的操作。
- 要向決策者或客戶展示概念，靜態圖講不出流程感。
- 何時不該做：要驗證的是「用戶要不要這個功能」，訪談或假門測試（fake door）更便宜；流程很標準、團隊已經做過很多次；或做 Prototype 的時間已經接近直接開發的時間。

## 動手前先問

1. **這個 Prototype 要驗證什麼假設？** 若沒答：不要開工。先幫對方寫一句「我們相信 ____，如果 ____ 就代表錯了」。
2. **給誰用？**（受測用戶、老闆、客戶、RD）若沒答：假設是給受測用戶，保真度以「能完成任務」為準。
3. **測完之後會做什麼決定？** 若沒答：先列出兩個可能的決定（做／不做，或 A 方案／B 方案），否則測了也不知道怎麼用。
4. **時間預算多少？** 若沒答：假設 PM 或設計師 1–3 天（假設值），超過就要重新評估是否值得。

## 做法

1. **寫下假設與判斷門檻。** 判斷標準：門檻事前寫定，例如「5 位受測者中至少 4 位能在不提示下完成」（假設值），而不是測完再看感覺。
2. **選保真度。** 依假設選，不是依時間多寡選：
   | 要驗證的 | 保真度 | 常見做法 |
   |---|---|---|
   | 流程順序、資訊找不找得到 | 低（紙本、灰階可點擊） | 紙上原型、Wireframe 串連 |
   | 文案、版面理解、信任感 | 中（接近真實視覺，固定資料） | 設計工具的可點擊原型 |
   | 手感、動態效果、即時回饋、效能感 | 高（可輸入、真實互動） | 程式碼原型、AI 生成的可運作頁面 |
   判斷標準：保真度只做到假設需要的程度，多的部分會讓受測者評論錯的東西。
3. **畫出可點擊範圍。** 只做與測試任務相關的路徑，其他按鈕明確設為不可點或點了顯示「此功能未包含」。判斷標準：列一張「可點清單」，測試任務都能在清單內完成。
4. **準備真實內容。** 用接近真實的檔案、名稱、數量。判斷標準：受測者不會因為假資料太奇怪而出戲。
5. **自己先走一遍，再找一位同事走。** 判斷標準：同事不需要你解釋就能完成主要任務，或卡住的地方正是你想測的地方。
6. **測試與記錄。** 依 `18-usability-testing.md` 執行，對照事前門檻判讀。判斷標準：結論直接回答「假設成立／不成立／不確定，原因 ____」。
7. **決定 Prototype 的去留。** 判斷標準：驗證完就封存，不要直接把原型程式碼當正式開發基礎，除非 RD 評估過品質。

## 產出模板

- **報告格式：** 完整報告（外框見 `modes/report.md`）
- **標題：** Prototype 計畫：____（功能）
- **結論先講：** 這個原型要驗證 ____；看到 ____ 就往下做，看到 ____ 就調整。

下面是本文的模板。

```markdown
### Prototype 計畫：____

**假設**：我們相信 ____，因為 ____。
**若 ____，代表假設錯誤。**
**判斷門檻**：____
**測完要做的決定**：A ____ ／ B ____

**對象**：____　**保真度**：低／中／高，理由：____
**時間預算**：____ 天　**負責人**：____　**完成日**：____

### 可點擊範圍
| 任務 | 路徑 | 需要的畫面 | 狀態 |
|---|---|---|---|
| ____ | ____ | ____ | ____ |

**刻意不做**：____

### 結果
- 門檻達成：是／否（____ / ____）
- 主要發現：____
- 決定：____
- 原型去留：封存／交 RD 評估
```

## 品質檢查

- [ ] 有一句可被推翻的假設，以及事前寫定的門檻。
- [ ] 保真度的選擇有理由，對應到假設要驗證的面向。
- [ ] 有可點擊範圍清單，測試任務都在範圍內。
- [ ] 有寫「刻意不做」，避免範圍擴張。
- [ ] 時間預算有上限，超過時有重新評估。
- [ ] 結論對應到事前列出的決定，而不是只寫「回饋不錯」。

## 常見錯誤

- **沒有假設就開始做** → 覺得「先做出來看看」比較快 → 寫不出假設就先不做，回到需求分析或訪談。
- **保真度過高** → 想讓老闆或客戶驚豔 → 高保真會讓受測者評論顏色與細節，而不是流程；給決策者看的版本與測試用的版本分開。
- **原型做成半個產品** → 每次測試都想補一點 → 鎖定可點擊範圍，新增需求寫進下一輪計畫。
- **用 Prototype 問「你會不會用這個功能」** → 想一次驗證需求與介面 → 意願問題用訪談或假門測試，Prototype 只驗證「會不會用」。
- **直接把原型程式碼上線** → AI 工具讓原型看起來能動 → 原型通常沒處理錯誤、安全與效能，交 RD 評估後再決定是否重寫。

## 情境範例

健身 App 想在手機版訓練頁加入「拖曳調整訓練順序」。
- 假設：用戶看到當天的動作清單後，會自然長按並拖曳排序；若 5 人中少於 4 人在無提示下完成，代表需要額外引導（假設值門檻）。
- 決定：A 直接上線長按拖曳；B 加入「編輯順序」模式按鈕。
- 保真度：高，因為要驗證的是手感與拖曳回饋，用可在手機上操作的程式碼原型。
- 可點擊範圍：開啟一份 8 個動作的訓練 → 進入動作清單 → 拖曳排序 → 儲存並開始訓練。其他功能點了顯示「未包含」。
- 時間預算 2 天（假設值），負責人 ____。
- 結果：門檻達成 ____ / 5，決定 ____。原型封存，正式實作由 RD 重寫。
