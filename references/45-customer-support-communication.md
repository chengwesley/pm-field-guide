# 45 客服溝通

> 一句話：把客服工單變成可以排優先的產品洞察，並讓客服在上線前就拿到回答客戶需要的東西。

## 何時用

- 客服說「最近很多人在問 XX」，你想知道到底多少、是不是產品問題。
- 每月或每季整理客服回饋，作為 backlog 輸入。
- 新功能或改版要上線，要準備客服素材。
- 有客戶情緒升級（揚言退費、公開抱怨、要求找主管），客服轉到產品端。

何時不需要：單純帳務、帳號操作問題，已有標準處理流程，客服可自行結案。

## 動手前先問

1. **工單系統有沒有分類標籤？標籤可信嗎？** 若沒答：假設標籤不一致，先抽樣 ____ 張（例如最近 50 張）人工歸類再判斷。
2. **要看的時間範圍與產品範圍？** 若沒答：預設最近一季、單一產品。
3. **這次要回答的是什麼決策？** 例如「下季要不要修 XX」。若沒答：先做全貌分類，挑前三大問題深入。
4. **客服有沒有自己的處理指標（例如首次回覆時間）？** 若沒答：先問客服主管，產品變動可能影響他們的指標，要事先講。

## 做法

1. **抽樣讀原文，再看標籤。** 先讀 30–50 張原始工單，判斷現有標籤是否反映真正問題。判斷標準：同一個標籤底下出現三種以上不同的根因，表示標籤太粗，要重分。
2. **用兩層分類。** 第一層：類型（Bug、操作不會、功能缺少、帳務、效能、其他）。第二層：具體問題（例如「找不到下載按鈕」）。判斷標準：「操作不會」大量集中在同一個畫面，通常是設計問題而不是使用者問題。
3. **量化。** 每個具體問題記：工單數、影響帳號數、處理時間、是否付費客戶、是否造成退費或流失。判斷標準：沒有分母的數字不報。「上週 40 張」要配「佔總工單 ____%」或「每千位活躍用戶 ____ 張」。
4. **轉成產品洞察。** 寫成「____ 類使用者在 ____ 時遇到 ____，每月約 ____ 張工單、耗用客服 ____ 小時（假設值），建議 ____」，進 backlog 跟其他需求一起排。
5. **做客服素材。** 每個上線項目準備：一句話說明變了什麼、FAQ（至少涵蓋「為什麼改」「舊的去哪了」「怎麼用」「有問題找誰」）、已知問題與暫時解法、截圖或短影片。判斷標準：客服看完能在不問 PM 的情況下回答前五個最可能的問題。
6. **上線前後同步。** 上線前 ____ 天（依團隊節奏，建議至少 3 個工作天）給素材並開 15 分鐘說明；上線後 1–2 週每天或隔天看相關工單，有新問題當天補 FAQ。
7. **處理情緒升級案。** 步驟：先跟客服拿完整脈絡（不要讓客戶重講一次）→ 判斷是產品缺陷、預期落差還是個案 → 決定補償或例外處理由誰核准 → 給客服一段可用的回覆 → 事後檢討是否要改產品或改說明。涉及退費、補償金額、合約責任時，依公司授權流程，必要時請法務與相關主管確認。
8. **個資處理。** 工單常含姓名、email、合約內容。分析時去識別化，只取必要欄位；匯出的分析檔設保存期限並限制存取，符合台灣個資法、GDPR、CCPA 的告知、最小蒐集與保存期限原則。不要把含客戶資料的截圖貼進公開頻道或外部工具。

```markdown

|---|---|---|---|---|---|---|---|
| ____ | ____ | ____ | ____ | ____ | ____ | ____ | ____ |
- 前三大洞察：
  1. ____ 類使用者在 ____ 時遇到 ____，建議 ____
- 已進 backlog：____　暫不處理與理由：____

### 上線客服素材包
- 功能／改版：____　上線日：____
- 一句話說明：____
- 誰會受影響：____
- FAQ
  - 為什麼改？____
  - 原本的 ____ 去哪了？____
  - 怎麼用？____（截圖／影片連結 ____）
  - 遇到問題找誰？____
- 已知問題與暫時解法：____
- 升級窗口（產品端聯絡人）：____
```

### 話術

- 給客服的升級案回覆草稿：「很抱歉造成您的困擾。我們確認這是 ____ 造成的，目前 ____ 已經處理／預計 ____ 前修正。在那之前，您可以 ____。如果還有任何影響，請直接回覆這封信，我們會優先處理。」——先承認、說清楚原因與時間、給當下可行的做法，不推給使用者。
- 跟客服主管談素材時程：「這次上線我會在 ____ 前給你 FAQ 和已知問題，你們覺得還缺什麼，在 ____ 前告訴我，我補上。」——讓客服主動提需求，而不是被動接收。

## 品質檢查

- [ ] 分類前有抽樣讀過原始工單
- [ ] 每個數字都有分母或比較基準
- [ ] 洞察句寫了使用者、情境、問題、量級與建議
- [ ] 客服素材包涵蓋「為什麼改」與「舊的去哪了」
- [ ] 上線前有預留客服熟悉素材的時間
- [ ] 升級案有明確的核准人與回覆草稿
- [ ] 分析檔已去識別化，沒有客戶個資外流到不該去的地方

## 常見錯誤

- **只看工單數排序** → 免費用戶的大量小問題蓋過付費客戶的關鍵問題 → 加上付費客戶、退費、流失欄位一起看。
- **把「操作不會」歸為使用者的問題** → 同一個畫面反覆被問，通常是設計或文案問題 → 集中度高的「操作不會」要當產品問題處理。
- **上線當天才通知客服** → 客服第一批回覆只能說「我幫您確認」，客戶體驗打折 → 至少提前幾個工作天給素材與說明。
- **升級案讓客戶重講一次** → 情緒會再升一級 → 產品端先跟客服拿齊脈絡再介入。
- **把客服當收件匣不回饋** → 客服不知道回報有沒有用，之後就不報了 → 每月告訴客服哪些回饋進了 backlog、哪些上線了。

## 情境範例

訂房網站某季客服工單整理（數字皆為假設值）。

- 總工單 ____ 張；抽樣 50 張發現「訂單問題」標籤底下其實有三種根因：付款成功但確認信延遲、改日期後房價差額沒說明、取消政策沒在付款前顯示。
- 重分後最大宗：「確認信延遲，以為沒訂到」，約佔訂單類 ____%，其中重複下單 ____ 張。
- 洞察：住客在付款完成後，因為確認信延遲、付款完成頁也沒有明確的訂單成立提示，所以誤以為訂房失敗而重複下單或來電確認，每月耗用客服約 ____ 小時。建議：付款完成頁直接顯示訂單編號與「訂房已成立」，會員中心即時出現該筆訂單。
- 客服素材（上線後）：FAQ「為什麼我還沒收到確認信？」先引導到會員中心查訂單；截圖標示訂單編號的位置。
- 個資：分析檔只保留工單編號、分類、會員等級，移除姓名、email、電話與付款資訊。
