# 23 驗收條件

> 一句話：把「做完了」從各自的感覺變成一份 PM、RD、QA 都能逐條打勾的清單，讓爭議發生在開發前而不是上線後。

## 何時用

- 每個進 sprint 的 User Story 都要有，這是故事能被估時與驗收的前提。
- RD 說做完、PM 說不對，雙方吵的是「本來就沒講清楚」的部分。
- 需求涉及規則判斷（權限、金額、狀態、期限），口頭講一定會漏。
- 何時不需要：探索性的 spike、原型或內部實驗，寫「要回答的問題」與時間盒即可，不必寫完整驗收條件。

## 動手前先問

1. **這個故事的業務規則有哪些？** 有沒有上限、下限、例外、跟其他功能的互斥？
   若沒答：從 PRD 與系統邏輯（24）推出規則，標「假設，請確認」，並把不確定的規則列成問題帶進 refinement。
2. **失敗時使用者應該看到什麼？**（錯誤訊息、可否重試、資料是否保留）
   若沒答：預設「不遺失使用者輸入、告知原因、提供下一步」，具體文案標 ____。
3. **哪些情況是這個故事明確不處理的？**
   若沒答：寫一條「超出範圍」並註明由哪個故事處理。
4. **驗收由誰做、在什麼環境？**
   若沒答：假設 QA 在 staging 用測試帳號驗，PM 做最後業務驗收。

## 做法

1. **選格式。**
   | 情況 | 用哪種 | 原因 |
   |---|---|---|
   | 有明確使用者操作順序、前後狀態 | 情境式（Given/When/Then） | 能直接轉成測試案例與自動化測試 |
   | 一堆並列的規則、限制、顯示要求 | 規則式（條列「系統必須……」） | 用 GWT 寫會很囉嗦，條列反而清楚 |
   | 規則組合很多（3 個以上條件交叉） | 決策表 + 少量 GWT | 避免漏組合，見 24 |

   同一個故事可以混用：主流程用 GWT，顯示與限制用規則式。
2. **寫 Given/When/Then。** Given = 前置狀態（誰、什麼資料、什麼權限）；When = 一個動作；Then = 可觀察的結果。判斷標準：Then 必須是看得到或查得到的東西（畫面、資料、通知、記錄），不能是「系統正確處理」。一條只放一個 When，多個動作就拆成多條。
3. **三類案例都要有：**
   - 正常：主流程、最常見的成功路徑。
   - 異常：輸入錯誤、無權限、網路失敗、外部服務錯誤、重複提交、併發操作。
   - 邊界：上下限（0、1、上限、上限 +1）、空值、超長字串、特殊字元、時區與跨日、檔案大小臨界。
   判斷標準：至少一條異常、一條邊界；涉及數字或期限的，邊界值要明寫數字。
4. **做可測試性檢查。** 每條讀一遍，問：「QA 不問我能不能判斷通過或失敗？」以下字眼出現就要改寫：快速、友善、合理、正常、適當、等等、相關、支援。改法是換成數字、具體畫面或具體行為。
5. **標非功能條件。** 效能、相容性、可及性若對這個故事重要，寫成可量測的條件（例：____ 秒內，假設值）。不重要就不寫，不要每張都貼一樣的。
6. **refinement 時逐條念。** RD 與 QA 在會上提出的「那如果……」，就地補成新條件或寫進超出範圍。

| AC-03 | 異常 | ____ | ____ | ____（錯誤訊息：「____」） |

| 列表正確排序 | 依建立時間新到舊；同秒建立時依 ____ 排序 |

## 品質檢查

- [ ] 每條 Then 都是看得到或查得到的結果，沒有「正確」「正常」「適當」。
- [ ] 至少一條異常、一條邊界；有數字限制的，上限與上限 +1 都有寫。
- [ ] 每條只有一個 When。
- [ ] 錯誤訊息有具體文案或標 ____ 待補，而不是「顯示錯誤」。
- [ ] 有寫超出範圍，且指出由哪個故事處理。
- [ ] 找一個沒參與討論的 QA 讀，他不需要問你就能寫出測試案例。
- [ ] 規則與 PRD、系統邏輯文件一致，沒有兩份文件講不同數字。

## 常見錯誤

- **Then 寫成「系統成功處理」** → PM 腦中知道成功長什麼樣，就以為別人也知道 → QA 只能驗「沒噴錯」。改：寫出成功後畫面顯示什麼、資料變成什麼狀態、誰收到通知。
- **只寫 happy path** → 寫的時候想的是 demo 情境 → 上線後最多客訴來自重複點擊、網路斷線、權限不足。改：用「異常清單」逐項過：無權限、重複、失敗、逾時、併發、外部服務掛掉。
- **把 UI 細節當驗收條件** → 例如「按鈕在右上角、藍色」 → 設計一改，驗收條件就過時。改：驗收條件寫行為，視覺交給設計稿與設計驗收。
- **驗收條件跟 PRD 數字不一致** → PRD 改了上限沒同步 → RD 照一個、QA 照另一個。改：數字只在一處定義（PRD 或規則表），驗收條件引用編號。
- **開發完才寫** → 覺得寫驗收條件很花時間 → 失去在開發前抓出誤解的機會。改：沒有驗收條件的故事不進 sprint，當成團隊的 Definition of Ready。

## 情境範例

診所預約「病患取消預約」故事的驗收條件節錄（示意，非實際產品規格）：

| 編號 | 類型 | Given | When | Then |
|---|---|---|---|---|
| AC-01 | 正常 | 病患有一筆狀態為「已預約」的門診 | 點「取消預約」並選擇取消原因 | 預約狀態變為「已取消」，該時段釋出，診所端收到含原因的通知 |
| AC-02 | 異常 | 診所已先取消該預約（例如醫師停診） | 病患點開舊提醒連結並點「取消預約」 | 顯示「此預約已由診所取消」，不改變任何狀態 |
| AC-03 | 邊界 | 取消原因「其他」欄位上限 ____ 字（假設值） | 輸入 ____ +1 字 | 無法再輸入，字數提示顯示上限 |
| AC-04 | 異常 | 家長替兩名子女預約同一時段，其中一筆已報到 | 取消另一筆 | 只取消該筆，已報到者不受影響，預約人收到通知 |

- R-01：取消原因為必選。
- 提醒：取消原因可能透露病情，屬敏感個資，通知內容與取消紀錄的保存方式要符合個資法規；若涉及爽約限制或預付費用退還，規則定稿前交法務審閱。
