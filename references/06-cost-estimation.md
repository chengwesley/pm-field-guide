# 06 成本評估

> 一句話：在決定做之前，算清楚「要花多少、還會持續花多少、因此放棄了什麼」，再跟預期回報比。

## 何時用

- 新功能或新專案要進 roadmap，老闆問「要多少人、多久」。
- 要決定自己開發還是買現成服務或採用第三方元件（build vs buy）。
- 兩個專案搶同一批人，要比較投入產出。
- 專案進行到一半，要評估「繼續投入還是止損」。

何時不需要：已經排進 sprint 的小任務，用團隊平常的估點方式即可；純粹排時程與里程碑看 `27-schedule-management.md`。

## 動手前先問

1. **範圍定到什麼程度？** 有沒有 PRD、流程圖、或至少一份功能清單？
   若沒答：先用一頁「範圍假設」列出包含與不包含的項目，估算結果附上這份清單。
2. **估算要用來做什麼決策？**（排進 roadmap、比較方案、報預算）
   若沒答：假設是「比較 2–3 個方案的相對成本」，精度到 ±50% 即可，不需要做到逐任務。
3. **誰會實際做？** 有沒有這類工作的歷史資料？
   若沒答：找負責的 RD 主管一起估，並請他提供 1–2 個類似過往專案的實際耗時。
4. **預期回報是什麼？**（營收、留存、成本節省、合規必要）
   若沒答：至少寫出一個可量化的預期成果，標為「假設值」。

## 做法

1. **拆解到可估算的粒度。** 把工作拆成 2–10 人天的區塊（前端、後端、設計、QA、資料遷移、上線）。判斷標準：沒有任何一塊超過 10 人天，超過就再拆或標記為「高不確定」。
2. **用三點估算，不要只問一個數字。** 每一塊請負責人給：
   - 樂觀（O）：一切順利。
   - 最可能（M）：正常狀況。
   - 悲觀（P）：遇到常見問題，但不是災難。
   期望值 E = (O + 4M + P) ÷ 6；P 和 O 差距大的區塊就是風險所在，先處理或先做技術驗證。
3. **補上常被漏掉的工作。** QA 與回歸測試、設計來回、code review、文件、上線與監控、多語系、資安審查、客服教育訓練、應用商店審核等待時間。判斷標準：拿出上一個類似專案的實際工時對照，估算不應明顯低於當時。
4. **算隱性成本。**

   | 類型 | 要問的問題 |
   |---|---|
   | 維運 | 上線後每月要花多少人力維護、處理客訴、更新相依套件？ |
   | 基礎設施 | 雲端、第三方 API、授權費會不會隨用量成長？ |
   | 技術債 | 這次為了趕時間省下的，之後要花多少還？ |
   | 機會成本 | 這批人如果去做下一個優先項目，能帶來什麼？ |
   | 協調成本 | 跨團隊依賴會不會讓等待時間比開發時間還長？ |

5. **Build vs Buy 用同一張表比 3 年總成本。** 自建 = 開發 + 3 年維運 + 機會成本；購買 = 授權或訂閱費 + 整合開發 + 供應商風險（漲價、停止服務、資料存放位置）。判斷標準：核心差異化能力傾向自建；非差異化、成熟的通用能力傾向購買，除非有資料主權或法規限制。
6. **算投入產出比，並說明不確定性。** 投入產出比 = 預期年度回報 ÷（一次性成本 + 年度持續成本）。同時給「回報打五折」的情境，看結論是否仍成立。
7. **對外報數字時給範圍。** 報「6–9 週，最可能 7 週」而不是「7 週」，並附上前提條件。

## 品質檢查

- [ ] 有寫範圍假設，明列不包含的項目。
- [ ] 每個區塊都有三點估算，且是由實際執行的人給的。
- [ ] QA、上線、設計來回、審核等待等常漏項目都列了。
- [ ] 有列上線後的持續成本，不只一次性開發成本。
- [ ] Build vs Buy 用 3 年總成本比，並寫了供應商風險。
- [ ] 有機會成本與「回報打五折」的情境。
- [ ] 對外報的是範圍加前提，不是單一數字。

## 常見錯誤

- **PM 自己估工** → PM 估的通常偏樂觀，RD 不認同就不會為它負責 → 由執行者估，PM 負責確認範圍一致與追問悲觀情境。
- **只算開發，不算上線後** → 功能上線後每月都要處理客訴與相依更新，一年下來可能超過開發成本 → 至少列出維運人天與第三方費用。
- **只比授權費就決定 build** → 「買要每年 ____，自己做只要 3 人月」忽略了維運和機會成本 → 用 3 年總成本比，並把機會成本寫出來。
- **單一數字被當成承諾** → 估 7 週，大家記住 7 週，第 8 週就變成延誤 → 永遠給範圍與前提，前提改變時重新估。
- **範圍在估完後偷偷長大** → 估的是 A，做的是 A+B+C → 範圍假設寫進文件，變更時重估並通知。

## 情境範例

情境：線上課程平台評估「課程影片自動字幕」，比較自建語音辨識與串接第三方服務（以下皆為假設值，第三方費用需查證）。

- 範圍：支援中、英文字幕產生與講師後台手動修正；不包含翻譯。
- 自建：模型整合與調校 O/M/P = 20/35/60 人天 → 期望約 37 人天；加上講師後台字幕編輯介面 15 人天、QA 10 人天；年度維運約 24 人天。
- 採購：整合 12 人天、QA 6 人天；服務費隨上架影片時數成長，每年約 ____（需查證）。
- 3 年總成本：自建高於採購，且自建模型品質風險高（P 值為 O 的 3 倍），專業術語多的課程辨識率尤其難保證。
- 機會成本：自建會占用 2 位工程師約 2 個月，延後「影片播放器載入速度優化」。
- 建議：先採購，用 2 個月觀察字幕開啟率與完課率變化；若字幕成為學員訂閱的主要理由再評估自建。
- 提醒：課程影片可能包含講師與學員的聲音及個人資料，選擇供應商時需確認資料處理位置與保存期限，符合台灣個資法、GDPR、CCPA；與講師的授權合約是否允許將影片交給第三方處理，需交由法務審閱。

## 工具

- `scripts/estimate.py 工時.csv`，或 `--item "項目:樂觀,最可能,悲觀"`（可重複）：算每項的期望工時與標準差、合計，以及指定信心水準（`--confidence 80|90|95`）下可以對外承諾的數字。
- 悲觀值是樂觀值 3 倍以上的項目會被標出來，代表不確定性高，先拆小或先做技術探索再估。
- 對外報期望值，約有一半機率會超時。要承諾日期時用承諾值，並說明對應的信心水準。
