# 27 時程管理

> 一句話：排出一份大家相信、且能提早看出會不會延期的時程，而不是一個寫在簡報上的日期。

## 何時用

- 專案跨多個團隊或角色（RD、設計、QA、法務、行銷），工作之間有先後依賴。
- 有外部承諾的日期（客戶合約、展會、平台審核、季度目標）需要倒推。
- 專案已經延期一次，需要重排並說清楚新日期的依據。
- 何時不需要：單一團隊、用 sprint 節奏持續交付、沒有外部日期的工作。用 sprint 規劃加 backlog 排序就夠，不必另做甘特圖。

## 動手前先問

1. **日期是硬的還是軟的？** 錯過會怎樣（違約、錯過檔期、只是內部目標）？
   若沒答：當作軟日期處理，但請需求方確認「晚兩週的代價是什麼」。
2. **範圍定了嗎？** PRD 是否定案、哪些是 Must？
   若沒答：只對 Must 範圍排時程，Should 以下列為「時間允許才做」。
3. **誰在這個專案上、各自投入比例？**
   若沒答：假設每人 ____%（假設值）投入，並在資源調度（28）確認。
4. **有哪些外部依賴？**（第三方、法務審閱、App Store 審核、客戶提供資料）
   若沒答：至少列出法務、平台審核、第三方三類，各自問負責人要時間。

## 做法

1. **拆 WBS。** 從交付物往下拆（不是從部門往下拆），拆到每個工作包能由一個人或一個小組在 ____ 天內（建議 2–5 天）完成並被驗證。判斷標準：每個工作包都有明確的「完成證據」（合併的 PR、簽核的設計稿、通過的測試）。
2. **標依賴。** 對每個工作包問「開始前必須完成什麼」。只標真正的硬依賴；「最好先做」不算。外部依賴（法務、平台審核）用不同顏色標，它們最難控制。
3. **請執行者估時，用三點估計。** 問樂觀、最可能、悲觀三個數字，而不是一個數字。悲觀與樂觀差很大的項目，代表不確定性高，要先做 spike 或拆更細。
4. **找關鍵路徑。** 把依賴串起來，最長那條就是關鍵路徑；上面任何一項延誤，整個專案就延誤。判斷標準：PM 要能說出關鍵路徑上的每一項與負責人。關鍵路徑上的人不要被分派其他雜事。
5. **放緩衝。** 不要在每個工作包偷塞緩衝（大家會用光它），集中放在：
   | 位置 | 用途 |
   |---|---|
   | 專案尾端（上線前） | 吸收關鍵路徑整體的延誤 |
   | 外部依賴接回關鍵路徑的匯入點 | 法務、審核、第三方回覆不準時 |
   | 高不確定項目之後 | 新技術、首次串接 |
   緩衝大小可先用「關鍵路徑上各項（悲觀 − 最可能）」的合計做參考，再依風險調整。緩衝被用掉多少要公開追蹤。
6. **定里程碑。** 里程碑是「可驗證的狀態」，不是「某某開始」。好的里程碑：「設計稿經 RD 確認可行」「API 聯測通過」「UAT 簽核」。每個里程碑寫判斷標準與決策者。
7. **檢查估時偏誤。** 對照以下清單修正：
   - 只估寫程式，沒估 code review、測試、修 bug、部署。
   - 用 100% 工時估，忘了會議、支援、請假。
   - 參考的是「上次順利時」的速度。
   - 沒算等待時間（等審閱、等回覆）。
   如果團隊有歷史資料，用「過去估 vs 實際」的比例校正。
8. **延期時用三個槓桿，一次只動清楚的那個。**
   | 槓桿 | 何時用 | 代價 |
   |---|---|---|
   | 砍範圍 | 日期是硬的，有 Should/Could 可以延後 | 功能變少，需求方要同意 |
   | 延時間 | 範圍是硬的（法規、合約功能） | 商業機會、信任 |
   | 加資源 | 工作可平行、新人能快速上手、離截止還有足夠時間 | 交接成本，越晚加越沒用 |
   判斷規則：先砍範圍；範圍不能砍再延時間；加人只在工作確實可切開且離截止還遠時才有效。向上報告時三個選項並列，附各自代價，讓決策者選。

### 延期報告話術

「目前 ____ 延誤 ____ 天，在關鍵路徑上，尾端緩衝剩 ____ 天，不足以吸收。有三個選項：A. 把 ____ 延到下一版，可維持原日期；B. 範圍不動，上線延到 ____；C. 從 ____ 調 ____ 人支援，可縮短 ____ 天，但 ____ 專案會延 ____。我建議 A，因為 ____。需要你在 ____ 前決定。」
有效的原因：先講事實與緩衝狀態，再給有代價的選項與建議，最後要求決定期限，避免變成單純的壞消息。

## 品質檢查

- [ ] 每個工作包都有完成證據，而不是「進行中」就算。
- [ ] 估時是執行者給的，且有三點估計。
- [ ] 能說出關鍵路徑上的每一項與負責人。
- [ ] 緩衝集中放置且公開追蹤，不是藏在各工作包裡。
- [ ] 估時涵蓋 review、測試、修 bug、部署與等待時間。
- [ ] 外部依賴都有對方負責人與承諾日期。
- [ ] 里程碑都是可驗證的狀態，有決策者。

## 常見錯誤

- **PM 自己估時** → 想快點給老闆日期 → 執行者不認帳，延期時說「那不是我估的」。改：一定讓執行者估，PM 負責挑戰假設與找遺漏。
- **從日期倒推塞工作** → 老闆給了日期，PM 把工作壓進去 → 時程從第一天就不可能，大家知道但不說。改：先由下往上估，跟目標日期的差距攤開談，用三個槓桿收斂。
- **忽略法務、審核等外部時間** → 覺得「送出去就好」 → 上線前一週卡在審閱或平台審核。改：外部依賴提前問對方要時程，匯入點加緩衝。
- **延期時只延日期不說原因** → 怕被責怪 → 第二次延期時信任歸零。改：每次調整都說明哪個假設失效、用了哪個槓桿、新日期的依據。
- **晚期加人** → 以為人多就快 → 新人上手與溝通成本反而拖慢。改：離截止不到 ____（建議至少一個完整 sprint）時，加人只用在可獨立切開的工作上。

## 情境範例

健身 App「新課程系列」上線時程（數字皆為假設值）：

- 目標：配合 ____ 月新年健身檔期上線，硬日期（錯過要等下一檔活動）。
- 關鍵路徑：課程影片後製與上架（最可能 8 天）→ 播放與課表串接調校（5 天）→ QA 回歸（4 天）→ App Store 送審（外部，3 天）。
- 緩衝：送審匯入點 2 天、尾端 3 天。
- 第二週串接調校悲觀估到 9 天，尾端緩衝不足。
- 決策：保留 6 堂課中的 4 堂上線，2 堂延到下一版（砍範圍），維持日期。理由：日期為硬、每堂課可獨立上線。
- 已通知行銷調整活動素材中的課程數量。

## 工具

- `scripts/dates.py plan 工作項目.csv --start <開始日> --holidays <假日檔>`：依工作天、緩衝天與前置關係排出每項的起訖日（都附星期），並算出緩衝佔比。
- `scripts/dates.py add <日期> <工作天數>`：推算 N 個工作天後是哪一天。
- `scripts/estimate.py 工時.csv --confidence 90`：用三點估算算出各項工時的期望值與承諾值，排時程時用承諾值決定緩衝要留多少。
- 交付前用 `scripts/dates.py check <草稿檔>` 核對所有星期標註。假日檔請依當地政府公布的辦公日曆建立，不要自己猜。
