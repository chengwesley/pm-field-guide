# 44 QA 測試

> 一句話：從 PM 角度定義「測什麼、測到什麼程度、什麼狀況不能上線」，讓 QA 的力氣花在風險最高的地方。

## 何時用

- 功能開發進入尾聲，要跟 QA 對齊測試計畫與範圍。
- 驗收條件寫好了，想確認 QA 的測試案例有沒有涵蓋。
- 測出一堆缺陷，要決定哪些上線前一定要修。
- 上線前最後把關，決定 go／no-go。

何時不需要：RD 的單元測試、自動化測試架構選型（PM 只需知道覆蓋範圍）。業務使用者的實際驗收屬於 UAT，請看 `31-uat.md`。

### 與 31-uat.md 的分工

| | QA 測試（本篇） | UAT（31） |
|---|---|---|
| 問的問題 | 有沒有照規格做對？ | 這樣做能不能解決使用者的工作？ |
| 執行者 | QA 團隊 | 業務方、實際使用者代表 |
| 依據 | 驗收條件、規格、風險清單 | 真實業務情境與流程 |
| 時間點 | 開發完成後、UAT 之前 | QA 通過後、上線之前 |

## 動手前先問

1. **這次變動影響哪些既有功能？** 若沒答：請 RD 列出改到的模組，假設同模組的所有功能都要回歸。
2. **哪裡出錯後果最嚴重？** 例如付款、預約結果、資料遺失。若沒答：預設「資料正確性」與「金流」為最高風險。
3. **要支援哪些平台、瀏覽器、版本？** 若沒答：用上一版的支援清單，並查使用比例最高的前幾名（需查證）。
4. **上線日是否可移？** 若沒答：假設可移，不要讓日期決定品質門檻。

## 做法

1. **定測試範圍。** 列三欄：新功能、受影響的既有功能、這次不測的（並寫理由）。判斷標準：「不測」的項目要有人簽字同意，不能只是 QA 沒時間。
2. **由驗收條件推導測試案例。** 每條 Given/When/Then 至少展開：正常路徑 1 條、邊界值 1–2 條、異常 1–2 條。例如「檔案上限 20MB」要測 19.9MB、20MB、20.1MB、0 byte、損毀檔。判斷標準：每條驗收條件都對應到至少一個測試案例；有測試案例找不到對應的驗收條件，表示驗收條件漏寫，回頭補。
3. **依風險排測試順序。** 先測錯了會造成資料錯誤、金流錯誤、法律效力問題的部分，再測體驗類。
4. **分清嚴重度與優先級。**

   | | 定義 | 誰判斷 |
   |---|---|---|
   | 嚴重度（Severity） | 缺陷對系統的技術衝擊 | QA |
   | 優先級（Priority） | 什麼時候要修 | PM |

   嚴重度建議四級：S1 系統無法使用或資料遺失／S2 主要功能失效無替代做法／S3 功能異常但有替代做法／S4 外觀、文字。
   兩者不一定一致：logo 拼錯是 S4 但可能 P1；極少數舊裝置上的閃退可能 S2 但 P3。判斷標準：PM 調整優先級時寫一句理由（影響多少使用者、有沒有替代做法）。
5. **規劃回歸測試。** 至少包含：受影響模組的核心流程、歷史上常壞的地方、跟金流與資料相關的流程。判斷標準：回歸清單能在 ____ 小時內跑完（依團隊實際能量設定）；跑不完就要拆成必跑與輪替。
6. **上線把關。** 照準出條件逐條確認，不符合就 no-go，或明確記錄「帶著已知問題上線」的決定與負責人。
7. **測試資料不用真實個資。** 用假資料或去識別化資料；若必須用正式環境資料重現問題，取得授權、限縮範圍、用完刪除，符合台灣個資法、GDPR、CCPA 的最小蒐集與保存期限要求。

## 產出模板

- **報告格式：** 完整報告（外框見 `modes/report.md`）
- **標題：** 測試計畫（PM 版）：____（版本）
- **結論先講：** 測試範圍是 ____；阻擋上線的缺陷定義是 ____；目前可上線／不可上線。

下面是本文的模板。

```markdown
### 測試計畫（PM 版）
- 版本／功能：____　上線日：____
- 測試範圍
  - 新功能：____
  - 受影響既有功能：____
  - 不測項目與理由：____（同意人：____）
- 高風險區：____
- 平台／瀏覽器／版本：____
- 測試資料來源：假資料／去識別化資料（說明：____）
- 時程：測試 ____ ～ ____，回歸 ____，UAT ____

### 驗收條件 → 測試案例對照
| 驗收條件 | 正常 | 邊界 | 異常 | 案例編號 |
|---|---|---|---|---|
| AC-1 ____ | ____ | ____ | ____ | ____ |

### 準出條件（Go／No-go）
- [ ] S1、S2 缺陷：0 個未解決
- [ ] S3 缺陷：____ 個以下，且每個都有替代做法與修復排程
- [ ] 回歸測試必跑清單：全數通過
- [ ] 高風險區：全數測過
- [ ] 已知問題已同步客服（見 45）
- 決定：Go／No-go／帶已知問題上線（負責人 ____，日期 ____）
```

### 話術

- 被要求砍測試時間：「可以縮，但要選砍哪裡。我建議保留 ____ 和 ____，因為錯了會 ____。____ 先不測，風險是 ____，你同意的話我記下來。」——把「要不要測」變成「承擔哪個風險」，並留下紀錄。
- 跟 QA 對優先級有分歧：「這個嚴重度你判 S2 我同意。優先級我放 P3，因為只影響 ____ 版本，使用者約 ____（需查證），而且可以 ____ 繞過。你覺得這個判斷有漏掉什麼嗎？」

## 品質檢查

- [ ] 每條驗收條件都對應到至少一個測試案例
- [ ] 測試案例有邊界值與異常，不是只有正常路徑
- [ ] 「不測項目」有寫理由與同意人
- [ ] 缺陷的嚴重度與優先級分開記錄，PM 調整處有理由
- [ ] 準出條件在測試開始前就寫好，不是上線前一天才定
- [ ] 測試資料沒有使用未經授權的真實個資
- [ ] go／no-go 決定有書面紀錄與負責人

## 常見錯誤

- **把 QA 當最後一道防線** → 規格不清的問題拖到測試才發現，修改成本最高 → 讓 QA 參加 refinement，在驗收條件階段就提問。
- **嚴重度和優先級混用** → 所有 bug 都變「很急」，或真正急的被埋沒 → 嚴重度給 QA 判，優先級由 PM 判並寫理由。
- **準出條件上線前才談** → 時間壓力下標準會被一路放寬 → 測試開始前就寫好並請主管確認。
- **回歸只測改到的地方** → 共用元件改動常在別處出事 → 回歸清單要包含共用模組與歷史常壞區。
- **用正式環境的客戶資料測試** → 違反個資最小使用原則，也可能外洩 → 用假資料；必要時走授權與刪除流程。

## 情境範例

診所預約 SaaS 新增「醫師排班可中途調整」功能：診次開放預約後，櫃台仍可調整醫師的看診時段。

- 高風險區：已成立的預約不能被靜默刪除或改時段；操作紀錄要完整記錄排班變更（誰、何時、改了什麼）；改期通知含病患姓名與就診時段，屬個資，通知內容與紀錄保存方式請法務確認符合個資法規。
- AC-3「櫃台可在診次開始前調整醫師時段，受影響的已預約病患收到改期通知」展開：正常（診次延後 30 分鐘，已預約病患全數收到通知）、邊界（病患正在線上預約該時段時調整）、異常（診次已開始才調整，應被拒絕並提示）。
- 缺陷判斷：「排班調整後改期通知寄錯病患」S2、P1（涉及個資外洩，是否升為 S1 請與資安負責人確認）；「調整按鈕在某舊版瀏覽器跑版」S4、P3（使用比例需查證）。
- 回歸必跑：建立排班、病患線上預約、取消與改期、操作紀錄匯出。
- 準出：S1/S2 為 0；排班變更紀錄與改期通知案例全數通過；客服已拿到已知問題清單。
