# 21 PRD 撰寫

> 一句話：讓 RD、設計、QA、業務在動工前對「為什麼做、做到哪、怎樣算成功」有同一份答案，而不是各自腦補。

## 何時用

- 一個功能或專案需要兩個以上的角色協作（RD + 設計 + QA），且開發超過一個 sprint。
- 需求來自業務或客戶，內部對「要解決什麼」還有分歧，需要白紙黑字收斂。
- 要做取捨（砍範圍、延期）時，需要一份大家都簽過的基準來對照。
- 何時不需要：改文案、修單純 bug、一人兩天內能完成且無外部依賴的小改動。寫一則 ticket 加驗收條件就夠，硬寫 PRD 只是在製造沒人看的文件。

## 動手前先問

1. **這件事要解決誰的什麼問題？有什麼證據？**（客訴數、流失訪談、數據）
   若沒答：先用需求來源推一個問題敘述，標「待驗證」，並在未決事項列出要補的證據。
2. **成功長什麼樣？上線後看哪個數字、目標值多少、多久後看？**
   若沒答：先放一個主指標與護欄指標，目標值寫 ____，註明「上線前須定案」。不可上線後再補。
3. **有沒有硬限制？**（上線日期、法規、合約承諾、平台）
   若沒答：假設無硬日期，但在風險區列「若有外部承諾日期請告知」。
4. **專案多大？** 決定用輕量版還是完整版。
   若沒答：依下方規則自己判斷，在文件頂端註明用了哪個版本。

## 做法

1. **選版本。** 判斷規則：
   | 條件 | 用哪版 |
   |---|---|
   | 1 個 sprint 內、單一團隊、無外部依賴 | 輕量版（一頁：問題、目標、範圍、需求、驗收、指標） |
   | 跨 sprint、跨團隊、或有第三方串接 | 完整版 |
   | 涉及計費、權限、法規、資料遷移 | 完整版 + 系統邏輯與資料結構附件（見 24、26） |
2. **先寫問題，不寫解法。** 背景段落只寫「現在發生什麼、對誰造成什麼損失、證據」。判斷標準：把解法整段刪掉，讀者仍能理解為什麼要做。
3. **寫目標與非目標。** 非目標是 PRD 最有價值的一段：明確寫出「這版不做」的東西，尤其是利害關係人提過但被砍掉的。判斷標準：每一條非目標都能對應到某個人曾經問過的需求。
4. **劃範圍。** 用 In / Out / Later 三欄。Later 要寫觸發條件（例如「上線後企業版使用率達 ____ 再評估」），否則等於騙人。
5. **寫功能需求。** 每條需求一個編號（FR-01），寫成「系統必須……」或使用者故事；附優先級（Must / Should / Could）與對應的驗收條件連結。判斷標準：QA 讀完能直接寫測試案例。
6. **畫流程。** 至少一條主流程 + 主要異常路徑（失敗、取消、逾時、無權限）。複雜的狀態轉移拆到系統邏輯附件。
7. **定指標。** 一個主指標、1–2 個護欄指標（不能變差的）、量測方式（事件名稱、資料來源）、觀察期。
8. **列風險與未決事項。** 未決事項每條要有負責人與決定期限，沒有期限的未決事項會一路拖到開發中途爆。
9. **審閱。** 依序給 RD lead（可行性與估時）、設計（流程）、QA（可測性）、需求方（是否解決問題）。每輪改版在變更紀錄寫一行。

**涉及「免登入就能看」的功能**（分享連結、公開頁、邀請連結），非功能需求要逐項寫到下列檢查點；還沒定案的列進未決事項，不要留白：

| 檢查點 | PRD 要寫清楚的 |
|---|---|
| 連結權杖 | 不可猜測（長度與隨機性由 RD／資安決定），網址不含內容名稱或使用者 ID |
| 期限與撤銷 | 預設有效期限、能否手動撤銷、撤銷後多久失效；原內容被刪除或移動時連結怎麼處理 |
| 存取範圍 | 「唯讀」是否包含下載、匯出、複製內容；要不要密碼或限定 email |
| 防濫用 | 速率限制、錯誤嘗試鎖定、不讓搜尋引擎索引（noindex） |
| 存取紀錄 | 擁有者看得到誰、何時看過；紀錄保存多久 |
| 個資與告知 | 檢視者被記錄了哪些資料（IP、裝置）、隱私權政策是否要更新，交法務確認 |

## 品質檢查

- [ ] 把「功能需求」整段遮住，只看背景，仍看得出為什麼要做、不做會損失什麼。
- [ ] 至少有一條非目標，且是某位利害關係人真的要過的東西。
- [ ] 每條 Must 需求都對應到可測試的驗收條件，沒有「好用」「快速」「友善」這類無法驗證的字。
- [ ] 主指標有基準值、目標值、量測事件、觀察期，四項齊全。
- [ ] 異常路徑至少涵蓋失敗、無權限、取消三種。
- [ ] 每條未決事項都有負責人和日期。
- [ ] 涉及個資的欄位有寫告知同意與保存期限。
- [ ] 功能有「免登入存取」時，6 個安全檢查點都已寫到，或列進未決事項。

## 常見錯誤

- **把 PRD 寫成解法說明書** → 需求方給了畫面就照抄，問題段落空洞 → RD 無法提出更便宜的解法，做完才發現沒解決問題。改：先寫問題與證據，解法放在需求段，並註明「若有更低成本方案請提出」。
- **沒有非目標** → 怕得罪人所以不寫 → 開發中途被追加「順便做一下」，範圍悄悄膨脹。改：把被砍掉的需求寫進非目標，附原因，審閱時讓需求方確認。
- **指標上線後才補** → 覺得先做出來再說 → 結果找不到基準值、事件沒埋，成效無從判斷。改：PRD 定案條件之一就是指標表完整、埋點列入開發項目。
- **PRD 定案後不再更新** → 開發中的決定只留在 Slack / Mattermost 討論串 → QA 和客服照舊版文件測與回答。改：任何影響範圍或行為的決定，當天回寫 PRD 並記變更紀錄。
- **小功能硬套完整版** → 以為文件越完整越專業 → 寫三天、沒人讀。改：照版本規則，輕量版一頁就好。

## 情境範例

診所預約 SaaS「批次寄送回診提醒」PRD（輕量版節錄）：

- 問題：診所櫃台要提醒病患回診時，需逐位點「寄送提醒」，客服每月收到相關抱怨約 ____ 件（假設值，需查證）。
- 目標 G1：櫃台管理員可一次對多位「待回診」病患發送提醒。
- 非目標 NG1：自動排程提醒（業務提過，留 Later，觸發條件：批次提醒上線後使用率達 ____%，假設值）。
- FR-01：系統必須允許在回診名單勾選最多 ____ 位（假設值）狀態為「待回診」的病患並一次發送提醒。
- FR-02：已預約、已回診、已停止追蹤的病患不可被勾選。
- 主指標：發送後 7 天內完成回診預約率，基準 ____%、目標 ____%（假設值）。護欄：提醒簡訊退訂率不高於 ____%。
- 未決 Q1：同一病患 24 小時內是否限制提醒次數？負責人：PM，期限 ____。
- 提醒：回診提醒會帶出病患姓名、就診科別等資訊，病歷相關資料屬個資法的特種個資；提醒內容、寄送頻率與同意取得方式需符合個資法規，定稿前交法務審閱。

## 工具

- `scripts/prd_check.py PRD.md`：檢查結構是否完整（非目標、範圍、編號需求、驗收條件、主指標與護欄指標、異常情境、未決事項的負責人與期限），並列出模糊用語、未填的空格、沒有數字的指標句，都附行號。
- 這支只查結構與機械性問題，通過不代表內容好。內容仍要照上面的品質檢查逐條看。
- 有具體日期時，再跑 `scripts/dates.py check PRD.md` 核對星期。
