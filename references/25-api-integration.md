# 25 API 與系統整合規格

> 一句話：PM 不寫程式，但要讓我方 RD 與對方窗口對「誰傳什麼給誰、失敗了怎麼辦、對不上帳時聽誰的」有同一份白紙黑字的答案。

## 何時用

- 產品要接第三方服務（金流、身分驗證、雲端儲存、CRM、ERP、通知服務）。
- 企業客戶要求把我方產品接進他們的系統（SSO、Webhook、資料回寫）。
- 要開放我方 API 給合作夥伴或客戶使用。
- 內部兩個產品或兩個團隊之間要交換資料（例如海外團隊的 SDK 與本地團隊的產品）。
- 何時不需要：RD 已有成熟串接、只是升級對方 SDK 小版本且行為不變。讓 RD 讀 changelog 即可，PM 只需確認有沒有使用者可見的變化。

## 動手前先問

1. **串接要達成什麼業務結果？不串會怎樣？**
   若沒答：從需求來源推（例如「客戶要求成立的訂單自動進他們的 ERP」），標「待需求方確認」。
2. **資料往哪個方向流？誰是資料的權威來源（source of truth）？**
   若沒答：假設「誰產生資料誰是權威」，並把衝突處理列為未決。
3. **對方窗口是誰？有沒有文件、測試環境、SLA？**
   若沒答：先列「需向對方索取」清單，不要在沒有測試環境前承諾上線日。
4. **傳輸的資料含不含個資或合約內容？會不會跨境？**
   若沒答：假設含個資，把告知同意、最小蒐集、跨境傳輸列入必審項目。

## 做法

1. **寫整合目的與成功標準。** 一句話寫業務結果，一句話寫怎麼算成功（例：____% 的事件在 ____ 分鐘內同步，假設值）。判斷標準：對方窗口讀完也能說出「為什麼要串」。
2. **畫資料流向。** 用方框箭頭標出：誰發起、經過哪些系統、同步或非同步、即時或批次。每條箭頭標資料名稱。判斷標準：每條箭頭都能回答「如果這裡斷了，誰會先發現」。
3. **定認證與權限。** PM 要決定的不是技術方案，而是業務問題：用誰的身分呼叫（使用者授權還是系統帳號）、權限範圍最小要多少、授權失效時使用者要做什麼、金鑰誰保管與輪替頻率。技術方案（OAuth、API key 等）由 RD 提，PM 確認符合上述決定。
4. **定請求／回應契約。** 以「業務欄位表」形式寫，每個欄位的意義、是否必填、格式、範例、對應到我方哪個欄位。重點是**語意**：「status = done」到底是指已付款還是已出貨。技術格式由 RD 依此產出 OpenAPI 等正式文件。
5. **定錯誤與重試。** 把錯誤分三類談：
   | 類型 | 例子 | 業務決定 |
   |---|---|---|
   | 可重試 | 逾時、對方暫時無法服務 | 重試幾次、間隔、全部失敗後誰收到通知 |
   | 不可重試 | 資料格式錯、權限不足 | 使用者看到什麼、要不要人工介入 |
   | 部分成功 | 批次 100 筆成功 98 筆 | 整批回滾還是只補失敗的 |
   另外要求「冪等」：同一請求送兩次不會產生兩筆資料。PM 要問 RD「重送會不會重複扣款／重複建檔」。
6. **定限流與容量。** 問對方的呼叫上限、我方預估尖峰量（標假設值）、超量時的降級行為（排隊、延遲、提示使用者）。判斷標準：尖峰量估算要有依據（現有用戶數 × 使用頻率）。
7. **定版本與相容。** 對方改版會提前多久通知、舊版支援多久；我方開放 API 時的版本策略與棄用公告期。寫進合作條款或 SLA。
8. **定監控與對帳。** 誰看監控、什麼指標告警（錯誤率、延遲、積壓量）、多久對一次帳（雙方筆數與金額或狀態是否一致）、對不上時以誰為準、誰負責補資料。判斷標準：對帳規則要在上線前就寫好，不要等出事才吵。
9. **開聯合審閱會。** 我方 PM、RD、對方技術窗口一起逐段過，每段結尾問「有沒有哪裡你們的理解不一樣」，會後寄出決議並請對方書面確認。

### 跟對方窗口開場時可以說的話

「這份不是技術規格，是我們雙方對『什麼情況下會發生什麼事』的共識。技術細節讓 RD 之後直接對，但第 5 和第 8 段（錯誤和對帳）請你們業務端也一起確認，因為出事時是業務在接電話。」
有效的原因：把對方業務窗口拉進來，避免只有技術窗口點頭、業務規則卻沒人負責。

## 品質檢查

- [ ] 每條資料流都標了權威來源，雙方資料衝突時有答案。
- [ ] 欄位契約寫了語意，不只是型別；狀態類欄位的每個值都有解釋。
- [ ] 錯誤表至少有可重試、不可重試、部分成功、重複請求四種。
- [ ] 限流的我方尖峰量有估算依據，不是空寫。
- [ ] 對帳規則寫了頻率、以誰為準、誰補資料。
- [ ] 個資欄位逐一確認過是否必要，跨境傳輸有標示。
- [ ] 對方有書面確認（信件或會議紀錄），而不是口頭同意。

## 常見錯誤

- **PM 以為串接是 RD 的事** → 只丟一句「接一下 ____」 → RD 做完才發現業務規則（重試、對帳、權限）沒人決定。改：PM 負責第 1、2、5、8、9 段的業務決定，技術細節交 RD。
- **只看對方 API 文件就承諾日期** → 沒有測試環境、沒問限流 → 聯測時才發現帳號申請要兩週。改：取得測試環境並完成一次端到端呼叫之前，只給區間不給日期。
- **狀態值語意沒對齊** → 雙方都有「completed」但意義不同 → 上線後資料被誤判。改：契約表逐值寫語意，聯合審閱時逐值念一遍。
- **沒想過重複請求** → 網路不穩重送 → 重複建檔或重複扣款。改：每個寫入動作都問 RD「重送會怎樣」，寫進錯誤表。
- **對帳等出事再說** → 覺得上線初期不會有問題 → 兩邊數字對不上時沒人知道以誰為準，雙方互推。改：上線前定好對帳規則，上線第一週每天對一次。

## 情境範例

記帳 SaaS 與企業客戶的 ERP 串接（示意，非實際專案）：

- 目的：記帳 SaaS 中核准的傳票自動拋轉到客戶的 ERP，免去會計人員手動匯出再匯入。
- F1：記帳 SaaS → 客戶 ERP；資料：傳票（日期、科目、金額、稅額、交易對象）+ 原始憑證編號；觸發：傳票狀態變「已核准」；非同步 Webhook；權威來源：記帳 SaaS。
- 錯誤：客戶 ERP 逾時 → 重試 ____ 次（假設值），間隔遞增；仍失敗 → 通知客戶管理員並保留在記帳 SaaS 內可手動重送。
- 冪等：以傳票 ID 判斷，重送不建立第二筆傳票。
- 對帳：每日比對當日核准傳票的筆數與總金額和客戶 ERP 收到的數字，對不上以記帳 SaaS 為準，由我方 CS 協助補送。
- 個資：傳票的交易對象可能含個人姓名、身分證字號或銀行帳號；需確認客戶 ERP 所在地是否涉及跨境傳輸、雙方保存期限。
- 提醒：涉及帳務資料的傳輸、保存期限（含稅法要求的憑證保存年限）與責任歸屬，條款定稿前交由法務審閱。

對外使用前需經相關主管審閱。
