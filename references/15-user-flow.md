# 15 User Flow

> 一句話：把用戶從起點走到目標的每一步、每個分岔與每個出錯的地方畫清楚，讓設計、RD、QA 看同一張圖。

## 何時用

- 新功能有多個角色或多個分支（例如預約人、同行者、診所櫃台），光靠文字講不清楚。
- RD 估時或 QA 寫案例前，要先確認例外路徑有沒有被想到。
- 既有流程要改版，需要先畫出現況（as-is）再畫改後（to-be）。
- 何時不需要：單一畫面、單一動作的小改動；直接在 Wireframe 上標註就夠。

## 動手前先問

1. **用戶的起點在哪裡？從哪個管道進來？**（Email 連結、App 推播、首頁按鈕）若沒答：列出所有可能入口，先假設最高流量的那個是主入口。
2. **怎樣算完成？** 若沒答：以「用戶拿到他要的結果」為終點，不是「按下送出」。
3. **有哪些角色？各自看到什麼？** 若沒答：先假設單一角色，但在圖上留一條「其他角色」泳道待補。
4. **哪些失敗情況一定要處理？** 若沒答：預設四類：網路中斷、權限不足、資料不合法、外部服務失敗。

## 做法

1. **寫一句任務描述。** 「____（角色）要從 ____（起點）完成 ____（目標）。」判斷標準：起點和終點都是可觀察的狀態，一張圖只處理一個任務。
2. **先畫主流程（happy path）。** 只畫最常見、一切正常的路徑，控制在 5–10 步。判斷標準：非團隊成員看圖，30 秒內說得出這個流程在做什麼。
3. **加入分支。** 每個判斷點寫成是非問題（「是否已登入？」），列出所有出口。判斷標準：每個菱形的出口都有去處，沒有懸空箭頭。
4. **補異常與空狀態。** 對每一步問：失敗了怎樣？沒有資料時長怎樣？中途離開再回來時在哪裡？
   | 類型 | 例子 | 要決定的事 |
   |---|---|---|
   | 錯誤 | 上傳失敗、格式不支援 | 錯誤訊息、可否重試、資料是否保留 |
   | 空狀態 | 第一次使用、搜尋無結果 | 顯示什麼、引導下一步 |
   | 中斷 | 關掉 App、Session 逾時 | 回來時從哪一步繼續 |
   | 權限 | 沒權限、方案不支援 | 擋在哪裡、怎麼說明 |
   判斷標準：QA 讀圖就能列出測試案例，不用再問你。
5. **標記多角色與系統動作。** 用泳道區分用戶、其他角色、系統、外部服務。判斷標準：每個系統自動發生的事（寄信、通知、到期）都有標出觸發條件。
6. **統一標記法。** 判斷標準：全團隊用同一套圖例。
   | 符號 | 意義 |
   |---|---|
   | 圓角矩形 | 起點／終點 |
   | 矩形 | 用戶動作或畫面 |
   | 菱形 | 判斷（是非問題） |
   | 虛線框 | 系統自動動作 |
   | 紅色線 | 異常路徑 |
7. **走查。** 拉設計、RD、QA 各一人，沿著圖講一遍。判斷標準：走查中冒出的「那如果……」都已補進圖或列入待決。

## 產出模板

- **報告格式：** 完整報告（外框見 `modes/report.md`）
- **標題：** User Flow：____（任務）
- **結論先講：** 主流程共 ____ 步；最需要團隊決定的分支或異常是 ____。

下面是本文的模板。

```markdown
### User Flow：____

**任務**：____（角色）要從 ____（起點）完成 ____（目標）
**入口**：____、____
**終點（完成定義）**：____
**角色／泳道**：____、____、系統、外部服務

### 主流程
1. ____
2. ____
3. ____

### 分支
| 判斷點 | 是 → | 否 → |
|---|---|---|
| ____？ | ____ | ____ |

### 異常與空狀態
| 步驟 | 情況 | 系統行為 | 用戶看到 | 能否恢復 |
|---|---|---|---|---|
| ____ | ____ | ____ | ____ | ____ |

### 待決事項
| 問題 | 決策者 | 期限 |
|---|---|---|
| ____ | ____ | ____ |

圖檔連結：____
```

（文字版可以搭配 Mermaid flowchart 或設計工具繪製，連結放在圖檔欄。）

## 品質檢查

- [ ] 起點與終點都是具體可觀察的狀態，一張圖只有一個任務。
- [ ] 主流程不超過 10 步，非團隊成員看得懂。
- [ ] 每個判斷點的所有出口都有去處。
- [ ] 至少涵蓋錯誤、空狀態、中斷、權限四類異常。
- [ ] 系統自動動作與外部服務有獨立標示與觸發條件。
- [ ] 標記法有圖例，全團隊一致。

## 常見錯誤

- **只畫 happy path** → 主流程最好想，例外交給 RD 自己處理 → 每一步都過一次「失敗、空、中斷、權限」四問。
- **把多個任務塞進一張圖** → 想一次看全貌 → 一張圖一個任務，用「子流程」符號連到另一張。
- **把畫面清單當流程** → 從 Wireframe 倒推 → 流程描述的是用戶的決策與動作，同一個畫面可以出現在不同步驟。
- **終點設在「按下送出」** → 那是 PM 能控制的最後一步 → 終點設在用戶真的拿到結果，例如「所有同行者都收到預約確認」。
- **圖畫完沒人看就交出去** → 時程緊 → 安排 30 分鐘走查，比開發中來回問省時。

## 情境範例

診所預約「多人同行預約與改期」流程。
- 任務：預約人從選擇診所時段開始，到所有同行者都完成預約並收到確認通知。
- 泳道：預約人／同行者／診所櫃台／系統／簡訊服務。
- 主流程：選診所與科別 → 選時段 → 新增同行者 → 送出 → 系統暫時保留連續時段 → 櫃台確認 → 系統寄確認給預約人與每位同行者 → 看診前一天提醒。
- 分支：「該時段名額是否足夠所有同行者？」是 → 繼續，否 → 提示改成相鄰時段或換日。
- 異常：簡訊發送失敗（系統標示並通知預約人改用 Email）、改期時其中一位同行者的新時段已滿（顯示卡住的是誰，並可只改其他人）、保留時段逾時未送出（釋放名額並提示重新選擇）。
- 空狀態：預約人第一次進「我的預約」時無資料，顯示建立第一筆預約的引導。
- 待決：改期時是否允許把同行者拆到不同時段，決策者 ____，期限 ____。
- 提醒：同行者姓名、生日與就診科別屬敏感個資，代填他人資料需取得當事人同意並符合個資法規；通知簡訊不寫科別細節。
