# 46 跨國溝通

> 一句話：團隊不在同一時區、不用同一個母語時，靠書面、明確的期待與固定節奏，讓事情不用開會也能往前走。

## 何時用

- 跟海外子公司或其他海外團隊一起做功能、共用元件或 SDK。
- 會議時間怎麼排都有人在半夜或下班後。
- 訊息發出去對方已讀，但兩天沒動靜。
- 會議上大家都說「OK」，事後發現理解不同。

何時不需要：同時區、同語言、天天見面的團隊（看 `36-cross-department-communication.md` 即可）。

## 動手前先問

1. **各方的工作時間重疊幾小時？** 若沒答：先查時區差，假設只有重疊時段能同步討論，其他全部走書面。
2. **雙方的工作語言是什麼？誰用非母語？** 若沒答：假設至少一方在用非母語，所有重要內容都要有書面版本。
3. **對方的決策鏈是誰？** 對方團隊的負責人、能拍板的人可能不是會議上發言的人。若沒答：直接問「這件事在你們那邊誰可以確認？」
4. **雙方用什麼工具？** 若沒答：先確認共同可用的文件、任務、訊息工具，避免資訊分散在兩邊各自的系統。

## 做法

1. **排會只排需要即時討論的事。** 判斷標準：資訊同步、進度回報、文件審閱改走書面；只有需要來回辯論或做取捨的才開會。重疊時段有限，要留給這類事。
2. **輪流承擔不方便的時段。** 如果一定要在某方非工作時間開會，固定輪替，而不是永遠同一方配合。會議錄影或有書面摘要，讓無法參加的人能補上。
3. **書面優先，寫到不用問就看得懂。** 每則需求或請求包含：背景、要對方做什麼、期限（附時區）、完成長什麼樣、找誰問。判斷標準：對方在你睡著時看到這則訊息，不需要等你回覆就能開始做。
4. **處理語言落差。**
   - 短句、一句一件事，避免俚語、內部縮寫、雙關。
   - 關鍵術語建一份對照表（例如產品功能名稱、狀態名稱），兩邊用同一套詞。
   - 會議結束前請對方用自己的話複述決議，而不是問「有問題嗎？」
   - 繁簡用字與慣用語可能不同，例如功能名稱、介面文字，要在術語表裡對齊，不要假設對方會自動轉換。
5. **避免已讀不回。** 每個請求都附「我需要你在 ____（日期＋時區）前回覆 ____」。約定回覆規則：收到 1 個工作天內至少回「收到，預計 ____ 給答案」。判斷標準：超過約定時間沒回，先用另一個管道確認是否看到，而不是假設對方不配合。
6. **處理差異，不貼標籤。** 每個人表達同意、拒絕、提出疑慮的方式不同，這跟個人、團隊習慣、職位都有關，不要用國籍或地區去推論。實務做法：明確問「你們那邊有沒有任何疑慮？」「如果要做到，你最擔心哪一點？」把隱性的顧慮變成可討論的事項。
7. **跟海外子公司協作的實務。**
   - 共用程式碼或 SDK（例如共用的地圖 SDK）時，介面變更要走書面變更通知，寫明影響的產品與版本。
   - 兩邊的發版節奏、假期不同，排時程前先交換行事曆（假期、凍結期）。
   - 跨境資料傳輸（使用者資料、日誌）要先確認公司規範與適用法規（台灣個資法、GDPR、CCPA 及對方所在地法規），不要為了除錯方便直接傳正式環境資料。
   - 建一個雙方都能看的決議紀錄頁，避免同一件事在兩邊各有一個版本。

## 產出模板

```markdown
### 跨時區請求訊息
- 背景：____（一到兩句）
- 請你做：____
- 完成長什麼樣：____
- 期限：____（日期＋時區，例如 11/20（週五）18:00 GMT+8）
- 參考資料：____
- 有問題找：____（我不在線時可以找 ____）
- 請在 ____ 前回覆「收到」與預計完成時間

### 協作約定（專案開始時雙方確認）
| 項目 | 約定 |
|---|---|
| 同步會議時段 | ____（輪替方式 ____） |
| 書面管道 | 決議：____／任務：____／即時訊息：____ |
| 回覆時限 | 收到後 ____ 個工作天內至少回覆「收到＋預計時間」 |
| 工作語言 | ____（術語對照表連結 ____） |
| 決策人 | 我方 ____／對方 ____ |
| 假期與凍結期 | ____ |
```

### 話術

- 確認理解：「為了確定我們想的一樣，可以請你用自己的話說一下接下來你會做什麼嗎？」——比「有問題嗎？」更能抓出誤解，而且不會讓對方覺得被考。
- 催進度但不施壓：「想確認一下這則有沒有看到。如果 ____ 前來不及，告訴我卡在哪，我們一起調整。」——先假設是資訊沒到，而不是對方怠慢。
- 引出疑慮：「如果這個時程有任何讓你擔心的地方，現在說最好，我們還有空間調整。」

## 品質檢查

- [ ] 每則請求都有期限，且期限附時區
- [ ] 每次會議後 24 小時內有書面決議，雙方都能存取
- [ ] 有術語對照表，關鍵功能名稱兩邊一致
- [ ] 不方便的會議時段有輪替，不是固定一方承擔
- [ ] 決議有請對方複述確認，而不是只問「OK 嗎」
- [ ] 文件與訊息裡沒有對任何國家、地區、文化的概括描述
- [ ] 涉及跨境資料傳輸的事項已確認公司規範與適用法規

## 常見錯誤

- **把同時區的開會習慣搬過來** → 重疊時間被進度回報吃光，真正要討論的沒時間 → 進度改書面，會議只留給決策。
- **「OK」就當作同意** → 對方可能是聽懂了、也可能是不方便追問 → 請對方複述，並主動問疑慮。
- **用文化刻板印象解釋行為** → 會讓合作關係變質，也通常是錯的 → 回到具體行為與流程：是期限不清、資訊不足、還是優先級衝突？
- **訊息只寫「麻煩看一下」** → 對方不知道要看什麼、何時要、看完做什麼 → 用請求模板，寫清楚做什麼與期限。
- **決議散在兩邊的工具裡** → 兩個月後各自記得的版本不同 → 一個雙方都能看的決議紀錄頁。

## 情境範例

台灣的外送平台團隊要使用海外團隊維護的派單／地圖 SDK 新版「預估送達時間」功能。

- 時差：同時區（GMT+8），但雙方假期不同；專案開始時交換 ____ 季的假期與凍結期。
- 協作約定：每週二 ____ 開 30 分鐘同步會，只討論需要決策的議題；進度更新在共同任務板上。
- 術語對照表：「預估送達時間」「預計抵達」「ETA」在兩邊介面與文件中的對應名稱統一成一套，避免同一功能三種叫法。
- 請求範例：「請在 11/20（週五）18:00（GMT+8）前確認新版 SDK 的預估送達時間 API 是否向下相容 v____。完成長什麼樣：回覆相容／不相容與受影響的方法清單。」
- 會後複述：海外團隊負責人複述「11/20（週五）前回覆相容性，若不相容附遷移說明」，記入決議頁。
- 資料：除錯需要的路線與位置資料使用測試資料，不傳外送員與顧客的真實位置與地址（屬個資，跨境傳輸須符合個資法規）。
