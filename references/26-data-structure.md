# 26 資料結構

> 一句話：在 RD 建表之前，先把「要記下哪些東西、每個欄位是什麼意思、什麼時候刪」講清楚，否則上線後要的報表撈不出來，該刪的個資刪不掉。

## 何時用

- 新功能會產生新的資料物件（新的實體或大量新欄位）。
- 業務或管理層要一份新報表，現有資料撈不出來。
- 要做資料遷移、合併兩個系統、或與外部系統交換資料（見 25）。
- 法規或客戶稽核要求說明「你們存了什麼、存多久、怎麼刪」。
- 何時不需要：只是在現有物件上加一個不影響報表、不含個資的顯示欄位。在 PRD 註明，RD 自行決定即可。

## 動手前先問

1. **之後要回答哪些問題？**（報表、儀表板、客服查詢、稽核）
   若沒答：從 PRD 的成功指標反推，至少要能算出主指標與護欄指標。
2. **哪些欄位含個資或敏感資料？**
   若沒答：假設姓名、Email、電話、IP、裝置 ID、使用者上傳的內容、照片都屬個資，逐一標記。
3. **資料要保存多久？刪除時是真刪還是標記刪除？**
   若沒答：先標「保存期限 ____，依法務意見定」，預設業務資料軟刪除、個資到期後實際刪除或去識別化。
4. **有沒有現成的實體可沿用？**
   若沒答：請 RD 提供現有 ER 圖或資料表清單，先比對再新增，避免重複定義「用戶」「組織」。

## 做法

1. **由報表需求回推。** 先寫出最終要看的報表（列、欄、篩選條件、時間粒度），每一欄問「要從哪個實體的哪個欄位算出來」。找不到來源的，就是要新增的欄位或要埋的事件。判斷標準：每個報表欄位都能對應到一個資料來源。
2. **列實體與關係。** 實體 = 業務上的名詞（組織、使用者、專案、任務、負責人）。關係寫成一句話並標數量：「一個組織有多個使用者（1:N）」「一個任務有多位負責人，一位使用者可在多個任務中當負責人（N:M）」。判斷標準：每條關係都能用業務語言念出來，業務方聽得懂。
3. **寫欄位定義表。** 每個欄位：名稱、業務意義、型別（文字 / 數字 / 日期時間 / 選項 / 布林）、必填、唯一、預設值、範例、來源（使用者輸入 / 系統產生 / 外部帶入）、是否個資。PM 寫業務意義與規則，RD 補技術型別。
4. **定唯一鍵與必填。** 業務上什麼組合不能重複（例：同一組織內 Email 唯一）、什麼欄位缺了這筆資料就沒意義。判斷標準：說得出「如果重複了會發生什麼壞事」。
5. **設計狀態欄位。** 生命週期用一個狀態欄位，選項值對應系統邏輯（24）的狀態表；其他屬性（是否封存、是否置頂）用獨立欄位。重要的狀態變化要有時間戳記（completed_at），報表才算得出耗時。
6. **定軟刪除與生命週期。** 每個實體寫：建立 → 使用中 → 封存 → 刪除的條件與期限。分清楚三種刪除：
   | 方式 | 何時用 | 注意 |
   |---|---|---|
   | 軟刪除（標記 deleted_at） | 使用者可復原、需保留稽核 | 所有查詢與報表要排除已刪除資料 |
   | 去識別化 | 要保留統計但不需知道是誰 | 確認無法透過其他欄位反推 |
   | 實際刪除 | 個資到期、使用者行使刪除權 | 備份與下游系統也要同步處理 |
7. **整理資料字典。** 把欄位定義表、選項值說明、計算欄位公式集中一份，供 RD、資料分析、客服共用。判斷標準：新進的資料分析師只看字典就能寫出正確查詢。

## 品質檢查

- [ ] 每個報表欄位都能指到來源欄位，沒有「到時候再想辦法撈」。
- [ ] 每條關係都能用業務語言念出來，並寫了刪除時的連動行為。
- [ ] 時間欄位寫了時區；重要狀態變化都有獨立時間戳記。
- [ ] 唯一鍵說得出重複會造成什麼問題。
- [ ] 每個個資欄位都有蒐集目的、保存期限、刪除權的處理方式。
- [ ] 軟刪除的資料在指標定義中明寫排除。
- [ ] 選項值與系統邏輯的狀態表一一對應，沒有多出或缺少的值。

## 常見錯誤

- **先建表再想報表** → 開發時只顧功能能跑 → 上線後要算「平均完成時間」才發現沒存完成時間。改：從報表回推，PRD 指標表的每一項都要有資料來源。
- **一個欄位兩種意思** → 「status」同時表示流程狀態和付款狀態 → 報表永遠算不對。改：一個欄位一個意思，寫進資料字典。
- **軟刪除了但報表沒排除** → 以為刪掉就不見了 → 指標被已刪除資料灌水。改：指標定義表固定寫「排除條件」欄。
- **個資「先存著以後可能用到」** → 怕將來要用 → 違反最小蒐集，也增加外洩與刪除的成本。改：每個個資欄位要有當下的使用目的，沒有就不存。
- **刪除只刪主表** → 忘了備份、Log、分析資料庫、第三方 → 使用者行使刪除權時無法完整處理。改：生命週期表列出所有存放位置，刪除流程逐一涵蓋。

## 情境範例

線上課程平台「課程分享連結」資料結構節錄（示意）：

- 報表需求：每月建立的分享連結數、平均被開啟次數、過期前被手動停用的比例。
- 實體：分享連結（1 堂課程可有多個連結，1:N）；開啟紀錄（1 個連結有多筆開啟紀錄，1:N）。
- 欄位：link_id（唯一）、course_id（必填）、created_by、expires_at（時區 UTC，顯示時轉使用者時區）、disabled_at、status（active / expired / disabled）。
- 開啟紀錄含 IP 與裝置資訊 → 屬個資；保存 ____ 天（假設值，依法務意見）後去識別化，只留日期與國家層級統計。
- 刪除權：使用者刪除帳號時，其建立的連結立即失效，開啟紀錄於 ____ 天內（假設值）刪除，含備份。

個資實務提醒：依台灣個資法、GDPR、CCPA，蒐集前要告知目的並取得必要同意、只蒐集達成目的所需的欄位、訂出保存期限並到期刪除或去識別化、提供使用者查詢與刪除的管道；資料存放或傳輸到台灣以外地區時，要確認跨境傳輸的合法依據。具體期限與依據請法務確認。
