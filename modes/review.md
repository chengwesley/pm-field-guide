# 審查模式

使用者已經有一份文件，要的是「幫我看哪裡有問題」，不是重寫一份。這個模式的產出是一份審查意見：問題在哪、多嚴重、怎麼改。

## 何時用

使用者說「幫我看這份 PRD」「這份 Roadmap 有什麼問題」「送出去之前幫我檢查」「review 一下」，或直接貼上一份完成度很高的文件。

使用者只給大綱或幾句想法時不是審查，回到一般的產出流程。

## 文件類型對應的指南

讀對應指南的「品質檢查」和「常見錯誤」兩段就好，不用整份讀。

| 文件 | 對照的指南 | 可用的腳本 |
|---|---|---|
| PRD | 21、23，有狀態或權限再加 24 | `prd_check.py`、`dates.py check` |
| User Story／驗收條件 | 22、23 | `dates.py check` |
| Roadmap | 05、04 | `dates.py check` |
| GTM／上線計畫 | 32、31 | `dates.py check` |
| 需求排序表 | 08 | `rice.py`（重算分數） |
| A/B 測試計畫或結果 | 19、20 | `ab_test.py` |
| 成效報告、漏斗分析 | 34、13、20 | `funnel.py` |
| 市場或商業評估 | 01、03 | `market_size.py`、`unit_econ.py` |
| 時程、週報、風險登記 | 27、29、30 | `dates.py check`、`estimate.py` |
| 提案、給主管的簡報 | 47、40、48 | — |
| 對外訊息（給業務、客服、跨部門） | 41、45、36 | — |

## 步驟

1. **先確認三件事**：這份文件給誰看、他們要用它做什麼決定或動作、什麼時候要送出。讀者不同，嚴重度的判斷就不同。對話裡已經有的不問；缺一兩項時不要停下來等，帶著最合理的假設先審，在審查意見開頭寫明假設，以及假設錯了哪些項目的嚴重度會變。三項都不知道才先問。
2. **有檔案就先跑腳本。** PRD 跑 `prd_check.py` 找結構缺漏；有日期就跑 `dates.py check`；文件裡有可重算的數字（RICE 分數、轉換率、p 值、LTV）就用對應腳本重算。腳本找到的問題直接列入，不用再猜。
3. **逐條對照品質檢查清單。** 每一條在心裡回答：有做到、沒做到、做了一半。輸出只列沒做到和做了一半的，不用把整張對照表貼出來。腳本查到的項目如果對應的要求寫在指南的「做法」或「產出模板」（例如範圍要分 In／Out／Later、要有護欄指標），回頭讀那一段再評論。
4. **再用讀者的角度讀一次**，問三個問題：
   - RD／QA／業務拿到這份，能不能不問人就開始做？卡在哪一句？
   - 這份文件最脆弱的假設是哪一個？如果它錯了，哪些部分要重寫？
   - 有沒有互相矛盾的地方（範圍說不做、需求卻寫了；指標和目標對不上）？
5. **定嚴重度**（見下）。
6. **寫審查意見**，照下面的格式。

## 嚴重度

| 等級 | 判斷標準 | 例子 |
|---|---|---|
| 必改 | 不改就送出，讀者會做錯、做不了，或做出承諾後收不回來 | Must 需求沒有驗收條件；日期星期寫錯；兩段互相矛盾；數字算錯；對外承諾了沒確認過的日期 |
| 建議 | 不改也能用，但會多來回幾輪，或留下風險 | 沒寫非目標；指標沒有基準值；未決事項沒有負責人 |
| 可忽略 | 寫法、排版、用詞的偏好 | 段落順序；用詞不一致但不影響理解 |

表裡的例子是常見情況，不是規則。定級一律以這一題為準：「如果作者不改，下週會不會有人因此做白工？」會就是必改。同樣是「未決事項沒有負責人」，那個問題會擋住開工就是必改，不擋就是建議。

腳本的結果也要重新定級。`prd_check.py` 的「最該先補」是通用排序，不知道讀者是誰，也不看需求的優先級；例如缺驗收條件的如果是 Could 需求，通常只是建議。

## 輸出格式

```markdown
**我的理解：** 讀者是 ____，他們會用這份文件 ____，預計 ____ 送出。（假設的部分標明；假設錯了，哪幾項的嚴重度會變）

## 審查結論
**判定：** 可以送出／改完必改項目再送／建議重寫 ____ 段
**一句話：** ____（這份文件最大的問題是什麼）

## 必改（N 項）
| # | 位置 | 問題 | 為什麼嚴重 | 建議改法 |
|---|---|---|---|---|
| 1 | ____（章節或引用原文） | ____ | ____ | ____（給出可以直接貼上的改寫） |

## 建議（N 項）
（同上格式，可以寫得簡短）

## 做得好的地方
- ____（具體指出，作者才知道哪些要保留）

## 最脆弱的假設
- ____：如果它不成立，____ 要重來。驗證方式：____

## 腳本檢查結果
- ____（跑了哪支、找到什麼；沒跑要說明原因）

## 需要你確認的事（最多 3 件）
- ____（只列會改變上面判定或嚴重度的事）
```

## 規則

- **引用原文再評論。** 「第 3 節『提升使用體驗』沒有可驗證的門檻」比「目標不夠具體」有用得多。
- **每個問題都給改法。** 只說「驗收條件不夠清楚」等於把工作丟回去；寫出一條改好的驗收條件當示範。
- **不要整份重寫。** 除非使用者要求。重寫會蓋掉作者的判斷，也讓他看不出你改了什麼。
- **不替作者補事實。** 文件缺基準值，就寫「缺基準值」，不要自己填一個數字進去。可以舉常見的選項當例子（「護欄指標常見的有寄送失敗率、每月費用」），但要標明是例子，數值和最後的決定留給作者。
- **審查模式不派紅隊，也不套產出模式的步驟。** 這個模式本身就是審查，照本檔的步驟與輸出格式就好。
- **24 號系統邏輯指南只在需要時讀。** 文件有三個以上的狀態、不同角色的權限差異、或計費規則時才加讀；輕量 PRD 不用拿整份狀態矩陣的標準去要求。
- **必改項目不超過 7 項。** 超過代表文件還不到審查階段，直接判定「建議重寫」並說明從哪一段開始。
- **肯定要具體。** 「非目標寫了三條而且都附原因」是回饋；「整體寫得不錯」不是。
- **審查別人的文件時留意語氣。** 使用者可能要把你的意見轉給作者。評論對事不對人，用「這段」當主詞，不用「你」。

## 常見錯誤

- **把所有問題都標成必改** → 想表現得嚴謹 → 作者分不出先後，乾脆全部不理。改：用「下週會不會有人做白工」過濾。
- **只挑錯不給改法** → 覺得改是作者的事 → 作者不知道你要的標準長什麼樣。改：每項附一段可以直接貼上的改寫。
- **用自己的偏好當標準** → 沒對照清單，憑感覺審 → 意見因人而異，作者無所適從。改：每個問題都對得回指南的品質檢查或常見錯誤。
- **跳過腳本直接讀** → 覺得用看的就夠 → 日期星期、分數、p 值這類錯誤肉眼最容易漏。改：能算的先算。
